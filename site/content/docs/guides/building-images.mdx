---

Dockflow builds every service that has `build:` in your Compose file, on every deploy. It reads the same build keys as `docker compose build`. The image then travels to the server, sending only the layers the server lacks, and the service runs it pinned by digest.

```yaml title="compose.yml"
services:
  web:
    build:
      context: .
      target: runtime
      args:
        API_URL: https://${DOMAIN}/api
    healthcheck:
      test: ["CMD", "wget", "-qO-", "http://localhost:3000/healthz"]
    x-dockflow:
      routes:
        - domains: ["${DOMAIN}"]
          port: 3000
  worker:
    build:
      context: .
      dockerfile: worker.Dockerfile
```

```sh
dockflow deploy production
```

You have no registry to set up and nothing to push by hand. By default, images go to a registry that `dockflow server init` runs on the server itself.

## How images are built

On each deploy, after the `before_build` hooks and the rendering of [templates](/guides/templates/):

1. Dockflow interpolates the Compose build keys and writes a `docker buildx bake` definition from them. `${VAR}` in a build key takes its value from the environment's `vars` and secrets, as everywhere else in the Compose file.
2. The target platform is the server's architecture, read from its Docker Engine. An `arm64` server gets `linux/arm64` images, whatever machine builds them.
3. Bake writes each image as an OCI image layout in a temporary directory. The image is never loaded into your local Docker.

Bake receives these build keys: `context`, `dockerfile`, `dockerfile_inline`, `args`, `labels`, `target`, `cache_from`, `cache_to`, `no_cache`, `no_cache_filter`, `additional_contexts`, `pull`, `network`, `extra_hosts`, `ssh`, `shm_size` and `entitlements`. `privileged: true` becomes the `security.insecure` entitlement. As in Compose, paths are relative to the Compose file, and `dockerfile` is relative to the build context.

Other build keys:

| Build key | Handling |
|---|---|
| `platforms`, `tags` | Ignored with a warning: images are built for the server and tagged by Dockflow |
| `secrets` | Mounted with `RUN --mount=type=secret`, never kept in the image. See [Secrets in builds](/guides/secrets/#secrets-in-builds) |
| `isolation`, `ulimits`, `provenance`, `sbom` | Refused |

A built service's image is named after the app and the service. An `image:` key on a service that also has `build:` is replaced by that name.

### The builder

Bake runs on your current buildx builder, which must be able to export an OCI layout. The default `docker` driver can only do so with the containerd image store enabled.

When your builder cannot, Dockflow creates a builder named `dockflow` with the `docker-container` driver, and uses it from then on. Its build cache stays in that builder between deploys.

### Attestations are off

Bake runs with `BUILDX_NO_DEFAULT_ATTESTATIONS=1`. As a result, rebuilding unchanged code from the cache gives the same digest, and the plan is empty. With a provenance attestation, which records when the image was built, the same code built twice would give two different images, and a deploy that changes nothing would replace the containers.

<Callout type="warn">
A build argument that changes on every commit, such as `${DOCKFLOW_GIT_SHA}`, gives a new image on every deploy. That service is then replaced by every deploy.
</Callout>

## How images reach the server

### The server-local registry (default)

`dockflow server init` runs `dockflow-registry`, a registry container published on `127.0.0.1:5959` on the server. Only the server itself can reach it.

1. The CLI opens an SSH tunnel to that port and pushes each image as `127.0.0.1:5959/<app>/<service>:<version>`. Layers the registry already has are skipped. The `push.finished` event says how many were sent and how many were already there.
2. The agent on the server pulls `127.0.0.1:5959/<app>/<service>@sha256:…` into Docker, and the service runs that exact digest.

This works from Docker Desktop and from any CI runner: the CLI process makes the push through SSH, with no registry account.

The images of the releases in retention stay on the server, so a [rollback](/concepts/releases-and-rollbacks/) never needs a transfer. Older images are deleted after a successful deploy; see [Cleanup](/guides/cleanup/).

### An external registry

To push to GitHub Container Registry, Docker Hub or your own registry, set `registry:` in `dockflow.yml`:

```yaml title="dockflow.yml"
version: 1
app: shop
registry:
  url: ghcr.io/acme
  username: acme-bot
  password: ${GHCR_TOKEN}
  additional_tags: ["${DOCKFLOW_ENV}-latest"]
environments:
  production:
    vars:
      DOMAIN: shop.example.com
```

| Key | Type | Default | Description |
|---|---|---|---|
| `url` | string | required | The registry and namespace. Images are `<url>/<app>/<service>`. A leading `https://` and a trailing `/` are removed |
| `username` | string | none | The account to push and pull with. Goes with `password` |
| `password` | string | none | Its password or token, usually from a secret (`PRODUCTION_GHCR_TOKEN` here) |
| `additional_tags` | list of strings | `[]` | Tags pushed besides the version label |

The CLI pushes each image as `<url>/<app>/<service>:<version>`, plus each additional tag, skipping the layers the registry already has. The agent on the server then pulls it by digest with the same credentials. You don't log the server into the registry, and the credentials are not written to the server.

Like every top-level key, `registry:` can be set per environment, to push only some environments to a registry.

### The version tag

The image tag is the release's version label:

- `--version`, when given;
- otherwise the Git tag in CI (see [Deploying from CI](/guides/ci/#tags-select-the-environment-and-the-version));
- otherwise the short commit, with `-dirty` when the working tree has changes.

Characters a tag cannot hold become `-`. Services always run an image by its digest, never by its tag, so pushing the same tag twice is harmless.

## Building with Podman

On a machine with Podman instead of Docker:

```yaml title="dockflow.yml"
version: 1
app: shop
build:
  engine: podman
environments:
  production:
    vars:
      DOMAIN: shop.example.com
```

Services are built one after the other with `podman build`, from the keys `context`, `dockerfile`, `dockerfile_inline`, `args`, `labels`, `additional_contexts`, `target`, `cache_from`, `cache_to`, `no_cache`, `pull`, `network`, `extra_hosts`, `ssh` and `shm_size`. Each image is exported as an OCI layout and sent like a bake build.

Short image names in `FROM` resolve as Podman's `registries.conf` says. If your configuration has no default registry, write `docker.io/library/node:22` rather than `node:22`.

Podman builds run only on the machine running the CLI: `engine: podman` cannot be combined with `builder: remote`.

## Building on the server

With `build.builder: remote`, the build runs on the server's Docker instead of your machine. This suits a runner without Docker, a slow uplink with a fast server, or a server whose architecture your machine cannot emulate.

```yaml title="dockflow.yml"
version: 1
app: shop
build:
  builder: remote
environments:
  production:
    vars:
      DOMAIN: shop.example.com
  staging:
    build:
      builder: local
    vars:
      DOMAIN: staging.shop.example.com
```

You still need the `docker` CLI with buildx locally, but no local Docker daemon. The CLI forwards a local socket (in a directory only your user can enter) to the server's Docker socket over SSH, and runs bake against the server's default builder. The build context is sent to the server over SSH.

- **Without an external registry**, each image is loaded into the server's Docker and named after its content: `localhost/<app>/<service>:<first 12 characters of the image ID>`. Services run it by image ID, and nothing is transferred after the build.
- **With `registry:`**, the images are named for the registry, and the server's Docker pushes them there. Services run them by digest.

A remote build uses the server's CPU and disk while the current release is serving.

## `dockflow build`

`dockflow build` builds without deploying:

```sh
dockflow build production                   # build every service, check that it builds
dockflow build production --only web        # some services only
dockflow build production --push            # also send the images where a deploy would
dockflow build production --platform linux/arm64
```

| Option | Description |
|---|---|
| `--only <services>` | Build these services only, comma-separated |
| `--push` | Connect to the server, build for its platform, and push the images to the registry the environment deploys from: the server-local one, or `registry.url` |
| `--platform <os/arch>` | The platform to build for, without `--push`. Default: `linux/` and this machine's architecture |
| `--skip-hooks` | Do not run the `before_build` and `after_build` hooks |

Without `--push`, no server is needed: the images are built, then discarded. This makes it a check for branch builds in CI (see [Deploying from CI](/guides/ci/#building-on-every-branch)). With `build.builder: remote`, the build lands on the server, so `--push` is implied.

A deploy always builds the images it needs, even after `dockflow build --push`. With the build cache on the same builder, that second build takes seconds and pushes nothing new. To skip it in CI, deploy with `--skip-build`; see [Build in one job, deploy in another](/guides/ci/#build-in-one-job-deploy-in-another).

## When a build fails

A failed build stops the deploy with exit code 7, before anything changes on the server. Dockflow shows the last 40 lines of the build output; `--verbose` shows all of it as `build.log` events. See [Exit codes](/reference/exit-codes/).
