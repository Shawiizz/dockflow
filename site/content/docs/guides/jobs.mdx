title: Jobs and migrations
description: Run one-off containers such as database migrations before or after the services of a deploy, with Compose's depends_on or x-dockflow.run.
---

A job is a service that runs to completion instead of staying up: a database migration, a cache warm-up, an index rebuild. Dockflow runs it as a one-off container on the new release's image, streams its output, and stops or rolls back the deploy if it fails.

```yaml title="compose.yml"
services:
  migrate:
    build: .
    command: ["npm", "run", "db:migrate"]

  web:
    build: .
    depends_on:
      migrate:
        condition: service_completed_successfully
```

`web` waits for `migrate` to complete successfully, so `migrate` is a job that runs before the services, as `docker compose up` would run it. The same file works locally with Compose.

## Declaring a job

There are two ways, and both can be used in one file:

| How | Kind of job |
|---|---|
| Another service depends on it with `condition: service_completed_successfully` | `before` |
| `x-dockflow.run: before` on the service | `before`, without any service depending on it |
| `x-dockflow.run: after` on the service | `after` |

```yaml title="compose.yml"
services:
  warm-cache:
    build: .
    command: ["npm", "run", "cache:warm"]
    x-dockflow:
      run: after
```

A job takes the rest of its spec from Compose as written: image or build, command, environment, networks, volumes. It runs once, with `restart: no`, and is never kept as a running service.

## When jobs run

Jobs run in a `dockflow deploy` that changes services: one that creates, updates or removes a service, or changes routes. They don't run:

- in a deploy whose plan is empty, or that only changes uploaded files;
- in `dockflow rollback`: a rollback does not replay old migrations;
- in `restart`, `stop`, `scale` or `destroy`.

A change to the job alone does not make a plan. In practice, a job usually shares the image of a service (`build: .` on both), so a code change updates that service and the job runs with it.

## Order

Within a deploy:

1. Networks, volumes and [uploads](/guides/uploads/) are created or updated, so a job can read uploaded files.
2. The services and the `before` jobs run in `depends_on` order: a `before` job runs once the services it depends on are up (a migration after its database), and before the services that depend on it. A `before` job that depends on nothing runs before every service. `before_deploy` hooks of the `exec` kind run right before the first service changes.
3. The `after` jobs run, once every service has switched.
4. The [public checks](/guides/health-checks/#public-checks-healthendpoints) run, then the release is committed.

Jobs of the same kind run in `depends_on` order, and alphabetically when nothing orders them. A service a `before` job depends on is created or updated first, and is healthy when the job starts: on the very first deploy of an app, a migration that depends on its database (`condition: service_healthy`) runs once the database is up. Services the job does not depend on, but that depend on it, start after it.


## Output, timeout and failure

Each line the job writes is a `job.log` event, shown as `migrate │ <line>`, and a `job.finished` event gives its exit code. The container is removed once it has exited.

| Outcome | What happens | Exit code |
|---|---|---|
| The job exits with `0` | The deploy goes on | – |
| A `before` job fails | The deploy stops before any service changes: nothing was switched, and the current release keeps serving | 8 |
| An `after` job fails | The deploy rolls back: traffic goes back to the previous containers | 8 |
| A job runs past its timeout | It is killed, and the deploy stops or rolls back as for a failure | 8 |

The timeout is the environment's `deploy.timeout`, or 30 minutes when it is not set:

```yaml title="dockflow.yml"
version: 1
app: shop
environments:
  production:
    deploy:
      timeout: 20m
```

`deploy.timeout` also replaces the health timeout of every service; see [Health checks](/guides/health-checks/#the-container-healthcheck). `on_failure` does not apply to jobs: a failed job always stops or rolls back the deploy.

## Refused combinations

`dockflow validate` refuses:

| Combination | Why |
|---|---|
| `x-dockflow.routes` or `x-dockflow.health` on a job | A job serves no traffic |
| `x-dockflow.stateful: true` on a job | A job is not a long-running service |
| `deploy.replicas` above 1 on a job | A job runs once |
| A service that waits for an `after` job with `service_completed_successfully` | The `after` job runs after that service |
| `x-dockflow.run` with another value than `before` or `after` | |

## Example: database migrations

A web app with Postgres, migrating the schema before each new version starts:

```yaml title="compose.yml"
services:
  migrate:
    build: .
    command: ["npm", "run", "db:migrate"]
    environment:
      DATABASE_URL: postgres://shop:${DB_PASSWORD}@db:5432/shop
    depends_on:
      db:
        condition: service_healthy

  web:
    build: .
    environment:
      DATABASE_URL: postgres://shop:${DB_PASSWORD}@db:5432/shop
    depends_on:
      migrate:
        condition: service_completed_successfully
    healthcheck:
      test: ["CMD", "wget", "-qO-", "http://localhost:3000/healthz"]
    x-dockflow:
      routes:
        - domains: [shop.example.com]
          port: 3000

  warm-cache:
    build: .
    command: ["npm", "run", "cache:warm"]
    x-dockflow:
      run: after

  db:
    image: postgres:16-alpine
    environment:
      POSTGRES_USER: shop
      POSTGRES_PASSWORD: ${DB_PASSWORD}
      POSTGRES_DB: shop
    volumes: [pgdata:/var/lib/postgresql/data]
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U shop -d shop"]
      interval: 5s
    x-dockflow:
      stateful: true

volumes:
  pgdata: {}
```

`DB_PASSWORD` comes from the `PRODUCTION_DB_PASSWORD` secret. On a deploy of a new version, the plan reads:

1. `job.run migrate`: the migration runs on the new image, against the running database;
2. `service.update web`: the new web containers start and become healthy, and traffic switches to them;
3. `job.run warm-cache`: the cache is warmed with the new code.

`depends_on: db` on `migrate` keeps the file working with `docker compose up`, where Compose starts `db` first.

Because the previous web containers keep serving while `migrate` runs, and for a moment after it, a migration should keep the schema readable by the previous version: add columns and tables in one release, and remove what the old code still reads in a later one. If `migrate` fails, nothing has switched; if the new web containers then fail their checks, the deploy rolls back the containers but not the schema.

To run a command by hand with a service's spec, such as a console or a one-time script, use `dockflow run`; see [Day-2 operations](/guides/day-2/).

## Workers and recurring tasks

Jobs run during deploys only. Dockflow has no scheduler of its own: nothing runs on a timetable on the server. Two ways cover background work.

**A worker** is a long-running service without routes, such as a queue consumer. It gets the `start-first` strategy: the new container starts and becomes healthy before the old one stops, so for a moment both run. A worker that must never run twice, such as one that runs its own scheduler (`supercronic`, `node-cron`), asks for `stop-first`:

```yaml title="compose.yml"
services:
  worker:
    build: .
    command: ["npm", "run", "worker"]
    deploy:
      replicas: 2

  scheduler:
    build: .
    command: ["supercronic", "/app/crontab"]
    x-dockflow:
      rollout:
        strategy: stop-first
      health:
        grace: 10s
```

**A recurring task** can also run from your CI on a schedule, with `dockflow run`, which starts a one-off container with the service's spec and the image it currently runs, and exits with the command's exit code:

```yaml title=".github/workflows/nightly.yml"
on:
  schedule: [{ cron: "0 4 * * *" }]
jobs:
  report:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: curl -fsSL https://raw.githubusercontent.com/Shawiizz/dockflow/main/install.sh | sh
      - run: dockflow run production web -- npm run report:nightly
        env:
          DOCKFLOW_SECRETS: ${{ toJSON(secrets) }}
```

`run` reads `dockflow.yml` and the Compose files, so the job checks out the repository and gets every secret they use, as a deploy does.
