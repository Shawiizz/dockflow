Dockflow is one binary, `dockflow`, that you install on the machine you deploy from: your laptop or a CI runner. Nothing is installed on the server's host: the CLI brings what it needs there as containers.

## Install the CLI

<Tabs items={["Linux and macOS", "Homebrew", "npm", "Windows", "From source"]}>
<Tab value="Linux and macOS">

```sh
curl -fsSL https://raw.githubusercontent.com/Shawiizz/dockflow/main/install.sh | sh
```

This installs the newest release. To install a given version, pass `--version`:

```sh
curl -fsSL https://raw.githubusercontent.com/Shawiizz/dockflow/main/install.sh | sh -s -- --version v1.0.0-alpha.4
```

</Tab>
<Tab value="Homebrew">

On macOS and Linux, the repository is its own tap:

```sh
brew tap shawiizz/dockflow https://github.com/Shawiizz/dockflow
brew install dockflow
```

`brew upgrade dockflow` installs the newest release. Homebrew checks each binary against the checksum written in the formula, which the release workflow writes from the release's `SHA256SUMS`.

</Tab>
<Tab value="npm">

On Linux, macOS and Windows, with Node.js 18 or later:

```sh
npm install -g @dockflow-tools/cli
```

The package runs the binary of your platform, installed as an optional dependency (`@dockflow-tools/cli-<os>-<arch>`): no script runs at install time and nothing else is downloaded. Installing with `--omit=optional` leaves the binary out. In a project, `npm install --save-dev @dockflow-tools/cli` pins the version in `package.json`, and `npx dockflow` runs it.

</Tab>
<Tab value="Windows">

In PowerShell:

```powershell
irm https://raw.githubusercontent.com/Shawiizz/dockflow/main/install.ps1 | iex
```

This installs the newest release in `%LOCALAPPDATA%\Programs\dockflow` and adds that folder to your user `PATH`. To install a given version, or into another folder:

```powershell
& ([scriptblock]::Create((irm https://raw.githubusercontent.com/Shawiizz/dockflow/main/install.ps1))) -Version v1.0.0-alpha.4 -Dir C:\tools
```

`install.ps1` checks the binary as `install.sh` does, below. On Windows on ARM, it installs the `amd64` binary, which Windows runs emulated.

</Tab>
<Tab value="From source">

Building needs Go 1.27 and `make`:

```sh
git clone https://github.com/Shawiizz/dockflow.git
cd dockflow
make build
```

The binary is `./dockflow`. It is a development build: `dockflow version` prints `dockflow dev`. See [the agent binary](#the-agent-binary) if you deploy from a machine that is not Linux.

</Tab>
</Tabs>

### What the installer does

`install.sh` detects your system (Linux or macOS, `amd64` or `arm64`), then:

1. downloads `SHA256SUMS` and the binary `dockflow-<os>-<arch>` from the GitHub release;
2. when [cosign](https://docs.sigstore.dev/cosign/system_config/installation/) is installed, verifies the Sigstore signature of `SHA256SUMS`: it must have been signed by the repository's release workflow. Without cosign, it says so and checks the checksum only;
3. checks the binary against `SHA256SUMS`, and stops if it does not match;
4. installs it as `dockflow` in `/usr/local/bin` when that directory is writable, and in `~/.local/bin` otherwise. If the directory is not on your `PATH`, it tells you. In GitHub Actions, it adds the directory to `GITHUB_PATH`.

It needs `curl` or `wget`, and `sha256sum` or `shasum`.

| Option | Environment variable | Default | Effect |
|---|---|---|---|
| `--version <tag>` (`-Version`) | `DOCKFLOW_VERSION` | The newest release | The release to install, such as `v1.0.0-alpha.4`; the `v` is optional |
| `--dir <path>` (`-Dir`) | `DOCKFLOW_INSTALL_DIR` | `/usr/local/bin`, or `~/.local/bin` (`%LOCALAPPDATA%\Programs\dockflow` on Windows) | Where to install `dockflow` |
| – | `DOCKFLOW_RELEASES_URL` | `https://github.com/Shawiizz/dockflow/releases/download` | Where releases are downloaded from: a mirror holding `<tag>/<file>` |

For example, to install into `~/bin` without root:

```sh
curl -fsSL https://raw.githubusercontent.com/Shawiizz/dockflow/main/install.sh | sh -s -- --dir ~/bin
```

<Callout type="idea">
In CI, pin the version with `--version` so that a new release does not change your deploys unannounced. The [CI guide](/guides/ci/) has complete workflows.
</Callout>

## Check the installation

```sh
dockflow version
```

```text
dockflow 1.0.0-alpha.4
```

With an environment, `dockflow version production` prints the version deployed there instead. `dockflow --help` lists the commands, and `dockflow <command> --help` shows the options of one.

## Shell completion

`dockflow completion <shell>` prints a completion script for `bash`, `zsh`, `fish` or `powershell`.

<Tabs items={["bash", "zsh", "fish", "PowerShell"]}>
<Tab value="bash">

Needs the `bash-completion` package.

```sh
# current shell
source <(dockflow completion bash)
# every new shell, on Linux
dockflow completion bash > /etc/bash_completion.d/dockflow
# every new shell, on macOS with Homebrew
dockflow completion bash > $(brew --prefix)/etc/bash_completion.d/dockflow
```

</Tab>
<Tab value="zsh">

```sh
# once, if completion is not enabled yet
echo "autoload -U compinit; compinit" >> ~/.zshrc
# every new shell, on Linux
dockflow completion zsh > "${fpath[1]}/_dockflow"
# every new shell, on macOS with Homebrew
dockflow completion zsh > $(brew --prefix)/share/zsh/site-functions/_dockflow
```

</Tab>
<Tab value="fish">

```sh
dockflow completion fish > ~/.config/fish/completions/dockflow.fish
```

</Tab>
<Tab value="PowerShell">

```powershell
dockflow completion powershell | Out-String | Invoke-Expression
```

Add that line to your PowerShell profile to load it in every session.

</Tab>
</Tabs>

Start a new shell for the change to take effect.

## The agent binary

Each deploy runs the `dockflow` binary itself on the server, as a short-lived agent container (see [How it works](/concepts/how-it-works/)). The server needs the Linux binary of exactly your CLI's version, for its architecture. The CLI finds it this way:

1. if `DOCKFLOW_AGENT_BINARY` is set, it uses the file at that path;
2. if the CLI is itself the Linux binary for the server's architecture, it sends itself;
3. otherwise (macOS, Windows, or a Linux machine of another architecture), it downloads `dockflow-agent-linux-<arch>` from the release of its own version, and caches it in your user cache directory, under `dockflow/<version>/` (`~/.cache/dockflow/` on Linux). `DOCKFLOW_RELEASES_URL` replaces the download URL here too.

A released CLI is built with the SHA-256 of the release's agent binaries, and checks the download against it: a server only runs a binary from the same build as your CLI, whose origin the installer checked. A CLI built without them, from source with a version, checks the download against the release's `SHA256SUMS` instead.

The binary is sent to the server only when the server does not already have the agent image of that version, so this happens once per version and per server.

<Callout type="warn">
A development build (`make build`) has no release to download from. To deploy from macOS or Windows with one, build the Linux binary too and point `DOCKFLOW_AGENT_BINARY` at it:

```sh
CGO_ENABLED=0 GOOS=linux GOARCH=amd64 go build -o dockflow-linux-amd64 ./cmd/dockflow
export DOCKFLOW_AGENT_BINARY=$PWD/dockflow-linux-amd64
```
</Callout>

## Server requirements

`dockflow server init <admin>@<host>` (or `sudo dockflow server init` on the server itself) prepares a server from an administrator's account: it installs Docker on Debian and Ubuntu when it is missing, creates the deploy user and its key, and installs the switch and the registry. See the [Quickstart](/start/quickstart/). The server needs:

| Requirement | Why |
|---|---|
| Linux on `amd64` or `arm64` | The agent is a Linux binary for one of these architectures |
| Docker Engine 27 or later | `server init` installs it on Debian and Ubuntu; elsewhere, install it first. The CLI checks the version when it connects, and refuses older engines (exit code 4) |
| SSH as `root` or a user with passwordless `sudo`, for `server init` (or a root shell on the server) | It creates the deploy user `dockflow`, in the `docker` group, which every other command uses. A user of your own in the `docker` group works too, with [`server connection`](/reference/cli/#server-connection). Dockflow reaches the Docker socket through SSH stream-local forwarding, which OpenSSH allows by default (`AllowStreamLocalForwarding`); when the server refuses it, it falls back to `docker system dial-stdio`, which needs the `docker` CLI on the server |
| A known SSH host key | Every connection verifies it: pinned in the configuration or the connection string, or present in your `~/.ssh/known_hosts`. Nothing is trusted on first use |
| Ports 80 and 443 free, for the `builtin` edge | The switch publishes them and obtains TLS certificates. With the `external` edge, behind your own proxy, the switch listens on `127.0.0.1:8080` instead. See [The switch and edges](/concepts/switch-and-edges/) |
| Port 5959 free on loopback | The server-local registry listens on `127.0.0.1:5959`, unless you use `--no-registry` |
| Access to Docker Hub | To pull the switch (`caddy:2`) and registry (`registry:3`) images, and the public images of your apps |

<Callout type="warn">
A user that can use Docker is root on the server: anyone holding its SSH key can start a privileged container. Use a dedicated user and key per environment. See [Security](/project/security/).
</Callout>

On the machine you deploy from, building images needs Docker with buildx, or Podman. Apps that only use public images need neither. See [Building images](/guides/building-images/).
