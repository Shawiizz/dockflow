Dockflow deploys a Docker Compose app to your own server over SSH. You keep your `compose.yml`, add a small `dockflow.yml`, and run `dockflow deploy` from your laptop or from CI. Dockflow builds what changed, shows a plan, starts the new containers next to the old ones, moves the traffic once they are healthy, and rolls back on its own when something fails.

On the server, an app is a real Compose project: `docker compose -p <app>-<env> ps` and `logs` work on it.

## Who it is for

| You are | Typical setup | What Dockflow gives you |
|---|---|---|
| A solo developer | One server, one to five apps | `dockflow deploy`, HTTPS with automatic certificates, rollbacks |
| A small team | One server per environment, a few apps, CI | A plan before every change, a lock against concurrent deploys, rollback in one command |
| An agency | Several servers, many client apps sharing them | One switch per server in front of every app, each app in its own Compose project |

If you already deploy with `docker compose up` over SSH, Dockflow keeps that model and adds zero-downtime rollouts, releases, rollback, secrets from CI and TLS.

## Principles

**Compose as written.** The Compose file that runs with `docker compose up` on your laptop is the one Dockflow deploys. Dockflow adds a `dockflow.yml` and per-service settings under `x-dockflow`, a key Compose ignores. Compose features that need a single host, such as `depends_on`, `127.0.0.1:` port bindings, `devices` and `network_mode`, work as Docker defines them.

**Zero downtime by default.** A service with a route gets new containers next to the old ones. Traffic moves only once the new containers are healthy, and the old ones get time to finish the requests in flight. See [Rollouts](/concepts/rollouts/).

**Plan before change.** Every change is computed as a plan from what the server is actually running. `dockflow plan` prints it; `dockflow deploy` shows it and asks before applying it on a terminal. A deploy touches only what changed: a service whose spec is unchanged keeps its containers.

**A rollback that finishes.** The deploy runs on the server, in a short-lived agent container. If your laptop sleeps, the network drops or the CI runner dies, the agent still finishes the run or rolls it back. See [Releases and rollbacks](/concepts/releases-and-rollbacks/).

**One server per environment.** An environment is one Linux server running Docker Engine. There is no cluster and no orchestrator. Scaling up means a bigger server first.

**Nothing but Docker on the server.** Dockflow installs no daemon on the host. It reaches Docker through the Engine API over SSH, and what it runs on the server are containers: the switch (Caddy), a local registry, and an agent per run. Its state is a few files under `/var/lib/dockflow`. See [How it works](/concepts/how-it-works/).

**Everything from a laptop or CI.** The `dockflow` CLI is a single binary. The same commands work on your machine and in any CI provider; in CI, one secret per environment holds the connection to the server.

**Fail loudly.** An unknown key, a variable with no value, an unsupported Compose feature or an unverified SSH host key is an error, never a silent default.

## What Dockflow does not do

These are deliberate choices, not missing features:

- **No orchestrator.** No Swarm, no Kubernetes, no Nomad. Dockflow drives plain Docker containers on one host.
- **One server per environment.** Dockflow does not schedule containers across servers or build a network between them. Several independent servers per environment may come after version 1.0.
- **No server creation.** Dockflow does not call cloud provider APIs. You bring a server that runs Docker.
- **No metrics or log storage.** `dockflow logs` streams logs from the server; storing them is the job of the tools you already use.
- **No user management.** Whoever holds an environment's SSH key can deploy it. Access to the Docker socket is root on the server, and Dockflow does not pretend otherwise. See [Security](/project/security/).
- **No platform on the server.** No database, no web UI and no daemon to operate on the server.

## Status

<Badge text="Alpha" variant="caution" /> The current release is **v4.0.0-alpha.9**. The configuration format is `version: 1`, and it may still change before the 1.0 release.

What works today:

- deploying a Compose app to one server with zero downtime, with the `switch`, `start-first` and `stop-first` rollout strategies, health gating and automatic rollback;
- the switch with the `builtin` edge (ports 80 and 443, automatic HTTPS), the `external` edge behind your own proxy such as nginx, and `none`;
- building images with buildx bake or Podman, locally or on the server, pushed to a registry on the server or to an external registry;
- jobs (migrations) through `depends_on` conditions, internal and public health checks, `on_failure`;
- hooks, templates, incremental uploads, webhooks;
- releases, `dockflow rollback`, locks, and the day-2 commands: `logs`, `exec`, `run`, `cp`, `ssh`, `ps`, `status`, `details`, `diagnose`, `restart`, `stop`, `scale`, `prune`, `destroy`;
- deploys from CI with the version and environment taken from the tag;
- Compose `secrets:` and `configs:`, SOPS files, the published-port filter, plugins with the built-in `nginx` and `systemd`, the watchdog, shared networks and volume plugins, the `cloudflare` edge, route options and error pages, redirect, proxy and files routes, and full provisioning: SSH hardening, `--nginx`, `server cloud-init`, `server status`, `check`, `edge`, `upgrade` and `uninstall`, and `dockflow init` with CI workflows;
- backups with restic: Postgres, MySQL, MongoDB and Redis dumps, volumes with application-aware quiesce and custom dump commands, to a repository on the server or off-site, with retention, and restores, including production's data into staging (`backup run`, `list`, `restore`, `prune`).

M3 ends once a real production project, ValientRP, runs on it.

Also there: the MCP server, for AI assistants ([AI agents](/guides/ai-agents/)), and the GitHub Action, which comments the plan on pull requests ([CI](/guides/ci/#the-github-action)).

What comes next is v1.0, released as 4.0.0: the formats frozen, signed releases and installers, and the documentation complete.

The [roadmap](/project/roadmap/) has the details.
