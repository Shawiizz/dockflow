This guide deploys a small web app, an nginx container behind a route with HTTPS, to one server. You install the CLI, prepare the server with one command, deploy, deploy a change, and roll it back. It takes about ten minutes.

<Steps>

1. **Check the prerequisites.**

   You need:

   - a Linux server (`amd64` or `arm64`), freshly installed or not. Dockflow installs Docker on Debian and Ubuntu; on another distribution, install Docker Engine 27 or later first;
   - SSH access to it as `root`, or as a user with passwordless `sudo` (or a shell on it as root);
   - ports 80 and 443 of the server free and reachable from the internet;
   - a domain name whose DNS record points to the server, here `hello.example.com`.

   The full list is in [Server requirements](/start/installation/#server-requirements). If ports 80 and 443 already belong to an nginx on the server, follow [Behind nginx](/guides/behind-nginx/) for the server part.

2. **Install the CLI** on your machine.

   ```sh
   curl -fsSL https://raw.githubusercontent.com/Shawiizz/dockflow/main/install.sh | sh
   dockflow version
   ```

   Other systems and options are in [Installation](/start/installation/).

3. **Prepare the server.** From your machine, or on the server itself: the result is the same.

   <Tabs syncKey="init">
   <TabItem label="From your machine">

   ```sh
   dockflow server init root@203.0.113.10
   ```

   Dockflow connects with your SSH key (from `ssh-agent` or `~/.ssh`, or `-k <key>`) and generates the deploy key on your machine: the private key never reaches the server.

   </TabItem>
   <TabItem label="On the server">

   ```sh
   curl -fsSL https://raw.githubusercontent.com/Shawiizz/dockflow/main/install.sh | sudo sh
   sudo dockflow server init
   ```

   Installed with `sudo sh`, the CLI goes to `/usr/local/bin`, where `sudo` finds it. `sudo` does not search `~/.local/bin`, where a user install goes: there, run `sudo ~/.local/bin/dockflow server init`.

   Without an argument, outside a project, `server init` prepares the server it runs on. It reads the public address, the SSH port (from `sshd_config`) and the host key there, so there is nothing to type. Give `--host` when the CI reaches the server at a domain name or at an address the server does not see (behind NAT), and `--port` for a port `sshd_config` does not show. The deploy key is generated in memory, printed, and never written to disk.

   </TabItem>
   </Tabs>

   ```text
     connecting to 203.0.113.10:22 as root
     installing Docker from download.docker.com (debian bookworm)
     creating the user dockflow
     adding dockflow to the docker group
     installing the deploy key of dockflow
     connecting as dockflow with the deploy key
     installing the agent image dockflow/agent:v4.0.0-alpha.6
   ✓ 203.0.113.10 is ready (edge: builtin, deploy user: dockflow)

   The connection string below holds the deploy key: store it as the <ENV>_CONNECTION secret
   …

   eyJ2IjoyLCJzZXJ2ZXJzIjpb…
   ```

   `server init`:

   - installs Docker when it is missing, from Docker's own repository;
   - creates the deploy user `dockflow`, in the `docker` group, with an SSH key restricted to what Dockflow uses. The private key is never written on the server;
   - reconnects as `dockflow`, and installs the switch (`dockflow-switch`, Caddy), which publishes ports 80 and 443 and obtains certificates, and the server-local registry (`dockflow-registry`, on `127.0.0.1:5959`);
   - prints the **connection string**: the server, its host key and the deploy key, in one value.

   Every step can be run again: on a prepared server, it changes nothing.

   <Aside type="note" title="The host key">
   From your machine, Dockflow never trusts a server it cannot verify. If you have already connected to it with `ssh`, its key is in your `~/.ssh/known_hosts` and there is nothing to do. Otherwise `server init` stops and shows the server's fingerprint: compare it with the output of `ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub` on the server (your provider's console shows it too), then run again with `--host-key SHA256:…`.
   </Aside>

   Create a directory for the project, and store the connection string in a local `.env.dockflow` file, kept out of git. In CI, it becomes the `PRODUCTION_CONNECTION` secret ([Deploying from CI](/guides/ci/)).

   ```sh
   # .env.dockflow
   PRODUCTION_CONNECTION=eyJ2IjoyLCJzZXJ2ZXJzIjpb…
   ```

   ```sh
   echo .env.dockflow >> .gitignore
   ```

   <Aside type="caution">
   The connection string contains the deploy key: anyone holding it controls Docker on the server, which means root. Never commit `.env.dockflow`. If it leaks, run `server init` again (it installs a new key) and remove the old line from `/home/dockflow/.ssh/authorized_keys`.
   </Aside>

4. **Describe the environment.**

   Write `dockflow.yml` at the root of the project. The server comes from the connection string, so nothing about it appears here:

   ```yaml
   # dockflow.yml
   version: 1
   app: hello

   environments:
     production:
       vars:
         DOMAIN: hello.example.com
   ```

5. **Describe the app.**

   Write `compose.yml` next to `dockflow.yml`. It is a standard Compose file; the `x-dockflow` key adds a route, which Compose ignores.

   ```yaml
   # compose.yml
   services:
     web:
       image: nginx:1.27-alpine
       healthcheck:
         test: ["CMD", "wget", "-q", "--spider", "http://127.0.0.1/"]
         interval: 5s
         timeout: 3s
         retries: 3
       x-dockflow:
         routes:
           - domains: ["${DOMAIN}"]
             port: 80
   ```

   `dockflow init --domain hello.example.com` writes these two files for you, and with `--ci github` or `--ci gitlab` a CI workflow (see [`init`](/reference/cli/#init)).

   `${DOMAIN}` takes its value from the environment's `vars`. The route sends `https://hello.example.com` to port 80 of the container, and the healthcheck tells Dockflow when a new container is ready for traffic.

   Check the project without touching the server:

   ```sh
   dockflow validate production
   ```

   ```text
   production: valid, 1 services
   ```

6. **Look at the plan.**

   ```sh
   dockflow plan production
   ```

   ```text
   Plan: 1 to create, 0 to update, 0 to remove
     · network.create hello-production_default: does not exist
     + service.create web [switch]: new service
     · routes.apply hello-production: routes changed
   ```

   The plan is computed from what the server actually runs. Nothing is changed yet.

7. **Deploy.**

   ```sh
   dockflow deploy production
   ```

   On a terminal, `deploy` shows the same plan and asks for confirmation (`-y` skips the question; in CI there is no question). Then the agent starts `web`, waits for its healthcheck, points the route at it, and records release 1. The switch obtains a certificate for `hello.example.com` from Let's Encrypt on its own.

   ```sh
   curl https://hello.example.com/
   ```

   Since `dockflow.yml` has a single environment, you can leave out `production` in every command.

8. **Check the status.**

   ```sh
   dockflow status production
   ```

   It shows the current release, its version label (the short git commit, or the time of the deploy outside git), and the containers of each service. `dockflow ps` lists the containers and `dockflow logs web` shows their logs.

9. **Change something and deploy again.**

   Change the image tag in `compose.yml`:

   ```yaml
   # compose.yml
   services:
     web:
       image: nginx:1.28-alpine
   ```

   ```sh
   dockflow deploy production
   ```

   ```text
   Plan: 0 to create, 1 to update, 0 to remove
     ~ service.update web [switch]: image nginx@sha256:… → nginx@sha256:…
   ```

   The new container starts next to the old one. Once it is healthy, traffic moves to it, the old container gets 30 seconds to finish the requests in flight, and then it stops. No request fails during the switch. Deploying again without a change prints `Nothing to change.` and creates no release.

10. **Roll back.**

    ```sh
    dockflow rollback production
    ```

    This restores the previous release, with the same zero-downtime switch, from the image that is still on the server: nothing is rebuilt or downloaded. The rollback is itself a new release:

    ```sh
    dockflow releases production
    ```

    ```text
    SEQ  VERSION  STATUS                     CREATED               BY
    3    a1b2c3d  active (rollback to 1)     2026-10-26T14:12:40Z  alice  ← current
    2    e4f5a6b  superseded                 2026-10-26T14:08:02Z  alice
    1    a1b2c3d  superseded                 2026-10-26T14:03:11Z  alice
    ```

    `dockflow rollback --to 2` would restore release 2.

</Steps>

If a deploy fails, for example because the new container never becomes healthy, Dockflow switches back to the previous containers on its own and exits with code 8. See [Releases and rollbacks](/concepts/releases-and-rollbacks/).
