Dockflow backs up the stateful services of an app with [restic](https://restic.net): each backup is a snapshot, encrypted, deduplicated (a second backup stores only what changed) and checked. A service opts in with `x-dockflow.backup`, and `dockflow backup run` backs it up.

```yaml
# compose.yml
services:
  db:
    image: postgres:17
    environment:
      POSTGRES_DB: shop
      POSTGRES_PASSWORD: ${DB_PASSWORD}
    volumes: [pgdata:/var/lib/postgresql/data]
    x-dockflow:
      stateful: true
      backup:
        type: postgres
        keep: { daily: 14, weekly: 8 }
volumes:
  pgdata: {}
```

```sh
dockflow backup run production
dockflow backup list production
```

```text
SNAPSHOT  TIME                  SERVICE  RELEASE  SIZE
3f1c2a9b  2026-10-27 18:02:11Z  db       12       4.2 MiB
```

## What is backed up

A service is backed up when it is `stateful` and declares `backup`. Its `type` says how:

| `type` | How it is captured |
|---|---|
| `postgres` | `pg_dump --format=custom`, run in the service's own container, so the dump tool is the server's version. The user is `POSTGRES_USER` (default `postgres`), the database `database` or `POSTGRES_DB` |
| `volume` | The service's volumes and bind mounts, or those listed in `volumes`, read-only, with its writes stopped as `quiesce` says |
| `command` | The `dump` command, run in the service's container: its standard output is the backup. `restore` reads it back on its standard input |
| `mysql` | `mysqldump --single-transaction --routines --events` (or `mariadb-dump`) of `database`, `MYSQL_DATABASE` or `MARIADB_DATABASE`, or every database. The credentials are the image's: `MYSQL_ROOT_PASSWORD` or `MARIADB_ROOT_PASSWORD`, else `MYSQL_USER` and `MYSQL_PASSWORD` |
| `mongo` | `mongodump --archive`, of `database` or every database, as `MONGO_INITDB_ROOT_USERNAME` |
| `redis` | `redis-cli --rdb`, with `REDIS_PASSWORD` when it is set |

| Option | Type | Default | Description |
|---|---|---|---|
| `type` | string | required | See above. |
| `database` | string | the image's | `postgres`, `mysql`, `mongo`: the database to dump. |
| `dump_options`, `restore_options` | string | none | `postgres`, `mysql`, `mongo`, `redis`: extra arguments of the dump and restore tools, split on spaces, like `"--no-owner --no-acl"`. |
| `volumes` | list | every volume and bind mount | `volume`: the volumes, by their key in the Compose file, and bind mounts, by their path on the server, to copy. |
| `quiesce` | `stop`, `none` or map | `stop` | `volume`: how writes stop during the copy. `stop` stops the service's containers, then starts them again; `none` copies while it runs; `{ exec: { pre: [...], post: [...] } }` runs `pre` in the running container before the copy and `post` after, even when the copy fails. |
| `dump`, `restore` | argument lists | required for `command` | The commands of the `command` type. |
| `keep` | map | `{ last: 7, daily: 14, weekly: 8, monthly: 6 }` | The snapshots kept: `last`, `hourly`, `daily`, `weekly`, `monthly`, as restic's `forget --keep-*`. |

A game server is backed up without stopping it:

```yaml
# compose.yml
services:
  minecraft:
    image: itzg/minecraft-server
    volumes: [world:/data]
    x-dockflow:
      stateful: true
      backup:
        type: volume
        quiesce:
          exec:
            pre: ["sh", "-c", "rcon-cli save-off && rcon-cli save-all flush"]
            post: ["rcon-cli", "save-on"]
        keep: { hourly: 24, daily: 14 }
```

## Where backups go

Without configuration, backups go to a restic repository on the server, in the `dockflow-backups` volume. Its password is generated on the first backup and stored in `/var/lib/dockflow/backups/local.password`, readable by root only. The first backup says so: **keep a copy of that password elsewhere**, the backups cannot be read without it.

A repository on the same disk as the data does not survive the loss of the server. Send backups off-site with `backups` in `dockflow.yml`, with the storage's credentials from your [secrets](/guides/secrets/):

```yaml
# dockflow.yml
backups:
  repository: s3:s3.eu-west-1.amazonaws.com/acme-backups/${DOCKFLOW_APP}
  password: ${RESTIC_PASSWORD}
  env:
    AWS_ACCESS_KEY_ID: ${AWS_ACCESS_KEY_ID}
    AWS_SECRET_ACCESS_KEY: ${AWS_SECRET_ACCESS_KEY}
```

`repository` is any restic repository reachable from the server: `s3:` (AWS and S3-compatible storage such as OVH, Scaleway or MinIO), `b2:`, `azure:`, `gs:`, `sftp:`, `rest:`. `env` is passed to restic. The first backup creates the repository, and its bucket when the credentials allow it. Without `password`, Dockflow generates one, as for the local repository, in `/var/lib/dockflow/backups/<id>.password`.

The credentials of the databases never leave their containers: the dump and restore commands read them from the image's variables and pass them to the tool in a temporary file, never on a command line. The repository's password and the storage's credentials reach restic through a file on the server's tmpfs, readable by root and removed at the end of the run: never on a command line, in a container's configuration or on disk.

## How a backup runs

<Steps>

1. `dockflow backup run [<env>] [<service>]` takes the environment's lock: a backup and a deploy never run at the same time (`--wait-lock` on a deploy waits for the backup).
2. The agent opens the repository, creating it on the first backup, and backs up each service of the **current release** that declares `backup`, or the one named: what the server runs, not your working tree.
3. A dump streams from the service's container into restic, without a temporary file. A failed dump keeps no snapshot.
4. Each snapshot is tagged with the app, the environment, the service and the release, and gets the server's name as its host.
5. The service's retention is applied (`restic forget`), and once a day the space of forgotten snapshots is reclaimed (`--prune`).
6. `restic check` reads 1% of the repository's data, chosen at random, to catch corruption early.

</Steps>

A backup that fails exits with code 12, after backing up the other services. `backup run` needs only the connection string and the repository's secrets: it reads `dockflow.yml`, not the Compose files.

## Scheduling

Nothing runs on a schedule on the server. Run `dockflow backup run` from your CI on a schedule, or from any cron that has the connection string. The workflow `dockflow init --ci github` writes does it every night, and `--ci gitlab` when a pipeline schedule runs it; in an existing workflow:

```yaml
# .github/workflows/backup.yml
on:
  schedule: [{ cron: "17 3 * * *" }]
jobs:
  backup:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: curl -fsSL https://raw.githubusercontent.com/Shawiizz/dockflow/main/install.sh | sh
      - run: dockflow backup run production && dockflow backup run production --server
        env:
          DOCKFLOW_SECRETS: ${{ toJSON(secrets) }}
```

## Restoring

```sh
dockflow backup restore production db                          # the latest snapshot
dockflow backup restore production db --snapshot 3f1c2a9b      # one snapshot, by its id
dockflow backup restore production db --snapshot 2026-10-20    # the newest one taken by that day
dockflow backup restore staging db --from production           # production's data into staging
```

`backup restore` restores a snapshot into the service of the **current release**, under the environment's lock. It asks for confirmation on a terminal, and needs `--yes` without one.

- **A dump** streams from the snapshot into the running service, with options that stop at the first error: `pg_restore --clean --if-exists --single-transaction --exit-on-error` for Postgres, which also rolls back what it did; the `mysql` (or `mariadb`) client for MySQL; `mongorestore --archive --drop --stopOnError` for MongoDB; `restore` for the `command` type. `restore_options` adds arguments.
- **Redis** loads its data when it starts: the service is stopped, the dump becomes `/data/dump.rdb` in its container (the official image's data directory), and it starts again. With `appendonly yes`, Redis loads its append-only file instead: turn it off, or back Redis up as a `volume`.
- **Volumes** are restored with the service stopped, then started again. Each volume gets the snapshot's files, and loses those the snapshot does not have.
- **`--from <env>`** restores a snapshot of another environment of the same app, read from that environment's repository with its secrets: the one on the server when both run on the same server, or its off-site `backups.repository`.

A restore that fails exits with code 12, and says why.

## Retention and pruning

After each backup, the service's `keep` is applied: restic forgets the snapshots it does not keep, and once a day reclaims their space. `backup prune` does it now, with the services' retention or the one you give:

```sh
dockflow backup prune production                   # each service's keep
dockflow backup prune production db --keep-last 3  # db keeps its 3 most recent snapshots
```

Options: `--keep-last`, `--keep-hourly`, `--keep-daily`, `--keep-weekly`, `--keep-monthly`.

## The server's state

`/var/lib/dockflow` holds every release record, so the history `rollback` and `releases` read, the uploads, the routes and the server's settings. `--server` backs it up to the environment's repository:

```sh
dockflow backup run production --server     # /var/lib/dockflow, to production's repository
dockflow backup list production --server
dockflow backup prune production --server --keep-last 7
```

The snapshots are tagged with the server's name, apart from the services'; the default retention applies. The passwords in `/var/lib/dockflow/backups/` stay out: a snapshot that holds its own repository's password protects nothing. The point is to rebuild a lost server, so send these backups off-site.

On a new server, after `dockflow server install`, restic puts the state back:

```sh
restic -r <repository> restore latest --tag server=<name> --target /
```

Then `dockflow deploy` of each app runs on its history.

## Without Dockflow

The repository is a standard restic repository. With its password, restic reads it on its own: `restic -r <repository> snapshots`, `restic restore <id> --target <dir>`, or `restic dump <id> /db.pgdump > db.pgdump` for a dump. The repository on the server is in the `dockflow-backups` volume.
