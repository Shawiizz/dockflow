Dockflow deploys by reaching your server's Docker Engine over SSH. This page says plainly what that gives access to, which keys matter, what Dockflow checks for you, and where your secrets end up.

## Docker access is root access

Whoever can use the Docker Engine on a server is root on it: one `docker run` with a bind mount of `/` is enough. The SSH user Dockflow deploys with must be able to use Docker, so **that user, and every key that logs in as it, is root-equivalent on the server.**

Dockflow does not pretend otherwise with sudo rules, which would not contain anything. It limits who holds the keys:

- Use a dedicated deploy user and a dedicated key per environment, not your personal key.
- Store the key only where deploys run: your CI's secrets, and `.env.dockflow` on the machines of the people who deploy by hand.
- Remove the key from the server's `authorized_keys` when someone leaves or a secret store is compromised, and print a new connection string.

## SSH and host keys

Every connection verifies the server's host key. Nothing is trusted on first use: an unknown key is an error, not a prompt.

The key is checked against, in this order:

1. the fingerprint pinned in the connection string, or under `host_key:` in `dockflow.yml`;
2. otherwise, your `~/.ssh/known_hosts`.

```yaml
# dockflow.yml
version: 1
app: shop
environments:
  production:
    server:
      host: 203.0.113.10
      user: deploy
      host_key: "SHA256:uNiVztksCsDhcc0u9e8BujQXVUpKZIDTMczCvj3tD2s"
```

`dockflow server connection` connects first, verifying the key against `--host-key` or `known_hosts`, then writes the key it verified into the connection string. Get the fingerprint from the server itself, over a channel you trust (your provider's console, for example):

```sh
ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub
```

A key that does not match fails with `ssh.host_key_mismatch` (exit code 4). If the server was reinstalled, verify the new key on the server and print the connection string again. If it was not, do not deploy: something may stand between you and the server.

## Connection strings

A connection string is the base64 of a small JSON document: the server's address, user and host key fingerprint, and **the private key** (or, for servers that only accept passwords, the password). Base64 is an encoding, not encryption: anyone who has the string can log in to the server as the deploy user, which means root.

- Store it as a CI secret, `<ENV>_CONNECTION` (`PRODUCTION_CONNECTION`), or in `.env.dockflow`, which must stay out of git. Never commit it or paste it in an issue.
- Dockflow reads it like any other secret and masks it, and the key and password it holds, in its output.
- Prefer a key to a password.

If you would rather not keep the key in a secret, describe the server under `server:` in `dockflow.yml` and give the key through `DOCKFLOW_SSH_KEY` or ssh-agent instead. See [Environment variables](/reference/environment-variables/#connecting-to-the-server).

## What listens on the server

| Component | Listens on | Notes |
|---|---|---|
| The switch (Caddy) | `80` and `443` on every address with the `builtin` edge; `127.0.0.1:8080` by default with the `external` edge | Its admin API listens on no port: only on a unix socket, in a volume that only the switch and Dockflow's agents mount. Your app's containers share networks with the switch and cannot reach it. |
| The registry | `127.0.0.1:5959` only | Never reachable from outside, so it needs no authentication. The CLI pushes images to it through the SSH connection. |
| Agents | Nothing | One container per run, started through the Docker API, gone when the run ends. |

Your own services listen where their Compose `ports:` say. Docker's published ports bypass host firewalls such as ufw and firewalld: without the port filter below, `5432:5432` is open to the internet. Publish internal ports on loopback, `127.0.0.1:5432:5432`, or not at all: services of one app reach each other by name on their Compose networks.

## The port filter

`server init` installs a filter that drops new connections from outside to the ports Docker publishes, except:

- the ports apps list under [`firewall.public_ports`](/reference/dockflow-yml/#firewall), open to everyone or to their `from` ranges;
- 80 and 443 for the switch, with the `builtin` edge, and from Cloudflare's ranges only with the `cloudflare` edge; or the port of `--switch-listen` with the `external` edge when it is not on loopback;
- SSH.

It catches a `5432:5432` written out of habit: the port stays published, but only the server itself and its containers reach it. The plan warns about each port published on every interface that no app lists.

The filter is an iptables chain, `DOCKFLOW-FILTER`, that Docker's `DOCKER-USER` chain jumps to. It matches the port a connection was sent to, before Docker translated it, and leaves alone the traffic of Docker's bridges, loopback, and the ports the host itself listens on (your own nginx or sshd). A deploy, a rollback or a `destroy` that changes the ports applies the new rules, through a short helper container on the host's network, and writes them to `/etc/dockflow/filter.rules` and `filter6.rules`. The `dockflow-filter` systemd unit loads them again at boot, before Docker.

To go without it, run `server init --no-port-filter`; `server init --no-port-filter=false` turns it back on. The filter applies to every container of the server, Dockflow's or not: publish ports you need open and that no app lists on loopback, or opt out.

## Secrets

Secrets come from your CI's variables (`PRODUCTION_*`, or `DOCKFLOW_SECRETS`) and from `.env.dockflow`. Dockflow reads only the variables with the environment's prefix, plus `DOCKFLOW_SECRETS`: `PATH`, `HOME` and the rest of your environment never become secrets.

**What Dockflow guarantees:**

- **Masked output.** Every secret value is replaced with `***` in everything Dockflow shows or stores: events, build output, hook and job output, errors, `config show`, and the `--json` stream. Values shorter than 4 characters are not masked, because they would hide ordinary words.
- **No command lines.** Secrets never appear in a command line, on your machine or on the server, where other users could see them in the process list.
- **Not in the agent's environment.** The agent receives its run on its standard input, not through environment variables.
- **A missing secret is an error**, never an empty string.

**What you control:**

- **Container environment.** A secret you interpolate into a service, `${DB_PASSWORD}` in `environment:`, is part of that container's configuration. Anyone with Docker access on the server sees it with `docker inspect`, and it is recorded in the release record under `/var/lib/dockflow`, readable by root only.
- **Files.** A secret you render into a template or an upload is written into that file on the server.
- **Interactive commands.** `dockflow exec`, `dockflow run` and `dockflow ssh` connect your terminal to the command. Their output is the command's own and is not masked.

- **Secret files.** Compose `secrets:` are written to `/run/dockflow/secrets/<app>-<env>/`, on a tmpfs (Dockflow refuses to write them elsewhere), in a `0700` directory, and mounted read-only. They appear neither in `docker inspect` nor in release records, which keep only their hash. A copy of each is kept in `/var/lib/dockflow/apps/<app>-<env>/secrets/`, root's only, so the watchdog can write them again after a reboot; `secrets revoke` and `destroy` delete the copies with the files. See [Secrets and configs](/guides/secrets/).

- **SOPS files.** Secrets can be kept in git in a SOPS file encrypted with age. The CLI decrypts it in memory and never writes it in clear, except for `secrets edit`, in a temporary file it deletes.

## State on the server

Dockflow's state lives in `/var/lib/dockflow`, a `0700` directory owned by root, with `0600` files. Only the agent writes there. It holds the release records, which contain your services' full configuration, including interpolated values, and the copies of the Compose secret files. See [Server layout](/reference/server-layout/).

## Verified downloads

- **The installer** downloads the binary from the GitHub release, checks it against the release's `SHA256SUMS`, and, when [cosign](https://docs.sigstore.dev/) is installed, checks the Sigstore signature of `SHA256SUMS`, bound to this repository's release workflow. Without cosign it says that it checked the checksum only. Install cosign to get the signature check.
- **The agent binary.** When the CLI is not itself the Linux binary for the server's architecture, it downloads that binary over HTTPS from the release of its own version, checks it against `SHA256SUMS`, and only then caches it and sends it to the server. A mismatch stops with `agent.checksum_mismatch`, and nothing is sent. The CLI does not check the signature yet; that check comes with v1.0.
- `DOCKFLOW_AGENT_BINARY` replaces the download with a binary you provide. Dockflow does not check it: use it only with binaries you built or verified yourself.

## Remote builds

With `build.builder: remote`, the build runs on the server's Docker. The CLI opens a local unix socket forwarded to the server's Docker socket, and points the build at it. Whoever can connect to that socket controls the server's Docker, so it lives in a temporary directory only your user can enter (`0700`), and is removed when the build ends.

## Signed webhooks

Webhooks under `notify:` can carry a secret. Dockflow then signs each request's body with HMAC-SHA256 and sends the signature in a header:

```yaml
# dockflow.yml
version: 1
app: shop
notify:
  - url: https://hooks.example.com/dockflow
    secret: ${WEBHOOK_SECRET}
environments:
  production: {}
```

```http
POST /dockflow HTTP/1.1
Content-Type: application/json
User-Agent: dockflow
X-Dockflow-Event: run.finished
X-Dockflow-Signature: sha256=5d0c1e9a7b3f…
```

Verify it on the receiving side by computing the HMAC of the raw body with the same secret, and comparing in constant time:

```python
import hashlib, hmac

def verified(secret: bytes, body: bytes, header: str) -> bool:
    expected = "sha256=" + hmac.new(secret, body, hashlib.sha256).hexdigest()
    return hmac.compare_digest(expected, header)
```

Reject requests whose signature does not match. Use an `https://` URL, so the payload and its signature are not readable on the way.

## The deploy user and its key

`dockflow server init` creates the deploy user `dockflow`, in the `docker` group, and gives it a key:

- generated by the CLI (ed25519) and never written to disk: the private key exists only in the connection string printed at the end. With `server init <admin>@<host>`, it is generated on your machine and never reaches the server; with `sudo dockflow server init` on the server, it is generated there, in memory, and shown in that terminal only;
- installed in `~dockflow/.ssh/authorized_keys` with `restrict,port-forwarding,pty`, which turns off agent and X11 forwarding and re-enables only what Dockflow uses;
- one per run: running `server init` again adds a new key, so each environment or CI system can have its own. Remove a key you no longer use from `authorized_keys`.

The administrator's account is used for this run only, and its credentials are never stored.

## What provisioning sets up

`server init <admin>@<host>`, `sudo dockflow server init` and `server cloud-init` also, unless `--no-hardening`:

- add `/etc/ssh/sshd_config.d/50-dockflow.conf`: no password authentication, root by key only. While the administrator's account has no authorized key, passwords stay accepted, and the output says so: add your key, then run `server init` again;
- install fail2ban, with a jail for SSH;
- enable unattended security updates (`unattended-upgrades`) and time synchronisation;
- rotate Docker's logs, when they install Docker.

`--from 203.0.113.0/24` restricts the deploy key to source addresses, with `from=` in `authorized_keys`. With `--nginx`, the deploy user gets two sudo rules, `nginx -t` and `systemctl reload nginx`, for the [nginx plugin](/guides/plugins/#the-nginx-plugin): a convenience, not containment, since the deploy user can reach Docker.

## Checklist

- One deploy user and one key per environment, stored only as `<ENV>_CONNECTION` in CI and in a gitignored `.env.dockflow`.
- Host keys pinned, checked on the server before you trust them.
- Internal ports published on `127.0.0.1`, or not published; public ones listed under `firewall.public_ports`.
- cosign installed where you run the installer.
- A secret on every webhook, verified by the receiver.
