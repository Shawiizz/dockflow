# CLI Commands

import { Callout, Tabs } from 'nextra/components'

Dockflow provides a comprehensive CLI for managing deployments and interacting with running services, on
either Docker Swarm or k3s. Most commands behave identically on both orchestrators; where they differ, or
where one orchestrator does not support a command at all, it is called out inline.

## Installation

<Tabs items={['npm (any OS)', 'npx (no install)', 'Linux / macOS', 'Windows']}>
  <Tabs.Tab>
    ```bash
    npm install -g @dockflow-tools/cli
    dockflow --version
    ```
  </Tabs.Tab>
  <Tabs.Tab>
    Run any command directly without installing:

    ```bash
    npx @dockflow-tools/cli <command>
    ```

    <Callout type="info">
      Pin a specific version with `npx @dockflow-tools/cli@1.2.3 <command>`.
    </Callout>
  </Tabs.Tab>
  <Tabs.Tab>
    ```bash
    curl -fsSL https://raw.githubusercontent.com/Shawiizz/dockflow/main/install.sh | bash
    dockflow --version
    ```
  </Tabs.Tab>
  <Tabs.Tab>
    ```powershell
    irm https://raw.githubusercontent.com/Shawiizz/dockflow/main/install.ps1 | iex
    dockflow --version
    ```
  </Tabs.Tab>
</Tabs>

The script detects your platform and architecture, downloads the binary, and adds it to your PATH.

<Callout type="info">
  The CLI binary is self-contained and requires no external dependencies for most commands.
  Use `dockflow setup` on the target Linux host, or `dockflow setup user@host` from any platform to configure a remote server via SSH — or `dockflow setup k3s <env>` to install and manage a whole k3s cluster, see [Setup: Initialize k3s](#initialize--update-k3s).
</Callout>

## Orchestrator Support

Not every command applies to both orchestrators — Helm and `dockflow volumes` are k3s-only,
`options.remote_build` and `dockflow exec --user` are Swarm-only, and so on. A command (or a flag
combination) that does not apply to the configured `orchestrator` **refuses before opening any SSH
connection**: it prints one message naming what is unsupported and why, a suggestion for what to do
instead, and exits with code `62`.

| Refusal | Message | Suggestion |
|---|---|---|
| `dockflow exec --user <user>` on k3s | `dockflow exec --user is not supported with orchestrator: k3s: the Kubernetes exec API runs commands as the container user` | Set `user:` in `docker-compose.yml`, or run `dockflow exec <env> <service> -- su -s /bin/sh <user> -c '<command>'`. |
| `options.remote_build: true` on k3s (`dockflow build`) | `options.remote_build is not supported with orchestrator: k3s (k3s nodes run containerd only); build locally or push to a registry` | Build locally (remove `options.remote_build`) or push to a registry. |
| `dockflow helm *` on Swarm | `dockflow helm <subcommand> requires orchestrator: k3s` | Helm releases are only supported on Kubernetes. |
| `dockflow volumes *` on Swarm | `dockflow volumes <subcommand> is not supported with orchestrator: swarm` | List Swarm volumes on a node with `dockflow ssh <env>`, then `docker volume ls`. |
| `dockflow prune --networks` on k3s | `dockflow prune --networks is not supported with orchestrator: k3s: the pod network is managed by the cluster` | — |
| `dockflow prune --volumes` on k3s | `dockflow prune --volumes is not supported with orchestrator: k3s: volumes are only deleted explicitly` | List them with `dockflow volumes list <env>`, then delete the ones you no longer need with `dockflow volumes rm <env> <name>`. |
| `dockflow prune --containers` on k3s | `dockflow prune --containers is not supported with orchestrator: k3s: the kubelet removes exited containers itself` | Reclaim image space with `dockflow prune <env> --images --all`. |
| any orchestrator command with `--server <worker>` | `--server` must name a manager (a k3s server), not a worker | — |

### Exit codes

Dockflow reserves the numeric codes below for its own failures; anything else is a bug or an
environment problem. `dockflow exec`/`bash`/`shell` are the one exception — they pass a container's
own exit code straight through as the process exit code, never wrapped as one of these.

| Code | Meaning |
|---|---|
| `0` | Success |
| `1`–`3` | Unknown / interrupted / a shelled-out command failed |
| `10`–`12` | Config not found, config invalid, servers.yml not found |
| `20`–`21` | Environment not found, no servers tagged for the environment |
| `30`–`32` | SSH connection failed, key not found, authentication failed |
| `40`–`43` | Runtime not available, stack/service/container not found |
| `44` | `ORCHESTRATOR_UNAVAILABLE` — kubectl/helm/docker missing, kubeconfig unreadable, the API unreachable, or the deploy identity was rejected |
| `50`–`53` | Deploy failed, deploy locked, rollback failed, health check failed |
| `60` | `VALIDATION_FAILED` — a config, servers.yml or compose problem (also `dockflow validate`'s failing exit code) |
| `61` | `INVALID_ARGUMENT` — a bad CLI argument, or `--server` naming a worker |
| `62` | `UNSUPPORTED_OPERATION` — the command or flag does not exist on the configured orchestrator (see the table above) |
| `70`–`73` | Backup failed, backup not found, restore failed, backup not configured |

## Connection Configuration

App commands require connection strings configured as CI secrets or in `.env.dockflow` for local development:

```bash
# .env.dockflow (for local CLI usage)
PRODUCTION_MAIN_SERVER_CONNECTION=eyJob3N0Ijoi...  # Base64-encoded JSON
STAGING_STAGING_SERVER_CONNECTION=eyJob3N0Ijoi...
```

The connection string is generated by `dockflow setup` and contains:
- `host`: Server IP or hostname
- `port`: SSH port
- `user`: Deployment user
- `privateKey`: SSH private key
- `password`: User password (optional)

<Callout type="info">
  Server names use underscores in secrets. A server named `main_server` in `servers.yml` uses `MAIN_SERVER` in the secret name.
</Callout>

<Callout type="info">
  All commands that accept an `<env>` argument support **prefix matching**: type `pr` instead of `production`, `st` instead of `staging`, etc. If the prefix is ambiguous, Dockflow will list the matching environments.
</Callout>

## Core Commands

### Deploy

```bash
dockflow deploy [env] [version]
```

Deploy the application to the specified environment. In CI, both `env` and `version` are auto-detected from the git tag or branch name.

| Option | Description |
|--------|-------------|
| `--only <services>` | Comma-separated list of services (or app-role Helm releases on k3s) to deploy |
| `--skip-build` | Skip the build phase |
| `--force` | Force deployment even if locked |
| `--accessories` | Deploy only accessories (force redeploy); no release record is written (K07) |
| `--all` | Deploy app + force redeploy accessories |
| `--skip-accessories` | Skip accessories check entirely |
| `--no-failover` | Disable multi-manager failover — use the first configured manager only |
| `--dry-run` | Preview the deploy without applying anything. **Still connects**: it resolves a control-plane node, reads the live cluster/stack state and runs the Helm plan (DESIGN-CORE C25); when no manager answers it prints one dim line saying the live plan was skipped and continues with the offline part. For a check that never opens a connection at all, use [`dockflow validate <env>`](#validate) |
| `--render` | With `--dry-run` on k3s: also print the rendered Kubernetes manifests, with every Secret's data replaced by `***` |
| `--branch <branch>` | Override auto-detected git branch |
| `--adopt <name>` | Take over a Helm release installed outside Dockflow (repeatable) |
| `--rebind-volumes` | Accept a claim-shape change that repoints a service at another PersistentVolumeClaim, instead of refusing |
| `-y, --yes` | Skip interactive confirmations |
| `--debug` | Enable debug output |

<Callout type="info">
  By default, Dockflow checks if `accessories.yml` has changed and automatically deploys accessories when needed. Use `--skip-accessories` to disable this.
</Callout>

<Callout type="warning">
  **k3s failure semantics.** A deploy that fails **after** the app was applied — a failing HTTP check, a fatal
  post-deploy hook, or an apply whose outcome could not be confirmed — keeps the release record: the cluster
  really is running that version, so `dockflow status` says so instead of pointing at stale state. When the
  configured `on_failure` is `rollback`, Dockflow re-applies the previous release's objects (Services, routes
  and workloads — PersistentVolumeClaims are never re-applied by a revert) rather than only the pod template a
  bare `kubectl rollout undo` would restore; a **first** deploy that fails leaves the workloads in place for
  debugging instead of deleting them, since there is nothing to revert to. See
  [Deployment](/en/deployment) for the full flow.
</Callout>

```bash
dockflow deploy production 1.0.0          # Deploy specific version
dockflow deploy staging                   # Auto-generated version
dockflow deploy production --accessories  # Force redeploy accessories only
dockflow deploy production --all          # Deploy app + accessories
dockflow deploy production --dry-run --render   # Preview and print manifests (k3s)
```

### Build

```bash
dockflow build [env]
```

Build Docker images locally without deploying. In CI, the environment is auto-detected from the git tag or branch name. Refused on k3s when `options.remote_build: true` — k3s nodes run containerd only and ship no image builder (see [Orchestrator Support](#orchestrator-support)).

| Option | Description |
|--------|-------------|
| `--only <services>` | Comma-separated list of services to build |
| `--push` | Push images to registry after build |
| `--skip-hooks` | Skip pre-build and post-build hooks |
| `--branch <branch>` | Override auto-detected git branch |
| `--debug` | Enable debug output |

```bash
dockflow build production                 # Build all services
dockflow build production --only app      # Build specific service
dockflow build production --push          # Build and push to registry
```


### Config

```bash
dockflow config [subcommand]
```

Display and validate project configuration.

```bash
dockflow config show     # or just: dockflow config
dockflow config validate # or: dockflow config check
dockflow config path
```

| Subcommand | Description |
|------------|-------------|
| `dockflow config show` (default) | Display current configuration |
| `dockflow config validate` (alias: `check`) | Validate configuration files against schemas |
| `dockflow config path` | Show configuration directory path |

Validation also warns about unknown keys: a key the schema does not declare is silently ignored at runtime (typos never fail a deploy), so `validate` flags each one with a "did you mean" suggestion when a close match exists — e.g. `backup.retention` → `Did you mean "retention_count"?`.

| Option | Applies to | Description |
|--------|-----------|-------------|
| `-j, --json` | show, validate | Output as JSON |
| `--verbose` | validate | Show detailed validation output |

### Validate

```bash
dockflow validate [env]
```

Validate `.dockflow` configuration files against their schemas. Runs entirely **offline** — no SSH
connection, no server, no orchestrator target resolved, ever — which makes it the fastest way to check
a config before pushing, and the one check `dockflow deploy --dry-run` is not (that one connects; see
[Deploy](#deploy)).

It checks `config.yml`, `servers.yml`, the presence of the compose file, and reports unknown keys with
a "did you mean" suggestion. It also fails on shell-style `${VAR}` placeholders in the compose file,
which Dockflow never substitutes (see [Docker Compose](/en/configuration/docker-compose)).

With an `<env>` argument and `orchestrator: k3s`, `validate` additionally renders both roles offline
(the same normalize + translate pipeline a deploy uses, with a synthetic `0.0.0-validate` version) and
reports every diagnostic the render would raise, plus the two topology rules that need no live node: an
even number of managers (2, 4, ...) and two servers naming the same node. `validate` without an
environment, or on Swarm, keeps today's output byte for byte.

| Option | Description |
|--------|-------------|
| `--debug` | Enable debug output |

```bash
dockflow validate                 # Validate every configuration file
dockflow validate production      # Also render both k3s roles offline for this environment
```

Exits `0` when everything is valid (warnings only still exit `0`), `60` (`VALIDATION_FAILED`) when a check fails.

## App Commands

These commands interact with deployed services via SSH (Swarm) or the Kubernetes API (k3s). Most
accept `-s, --server <name>` to target a specific manager (defaults to the first ready one).

### Logs

```bash
dockflow logs <env> [service]
```

View logs from running services. On Swarm, only **currently running task replicas** are streamed by
default — terminated and crashed replicas are excluded to avoid interleaved noise from past failures.
On k3s, `--all-tasks` includes the previous container of a crashed and restarted pod (the equivalent
of `kubectl logs --previous`), and `-c, --container <name>` selects one container of a multi-container
pod. Use `--pick` to select one specific instance interactively.

| Option | Description |
|--------|-------------|
| `-f, --follow` | Follow log output |
| `-n, --tail <lines>` | Number of lines to show, or `all` (default: `100`) |
| `-T, --timestamps` | Show timestamps |
| `--since <time>` | Show logs since a duration (`1h`), a date, or a timestamp |
| `-a, --all-tasks` | Include terminated/historical instances (Swarm) or a crashed pod's previous container (k3s) |
| `--pick` | Interactively pick which instance to follow |
| `-c, --container <name>` | Container of a multi-container pod (k3s) |
| `--no-prefix` | Never prefix lines with the instance label |
| `-s, --server <name>` | Target manager |

```bash
dockflow logs production                 # All services, running instances only
dockflow logs production app -f          # Follow specific service
dockflow logs production app -n 500      # Last 500 lines
dockflow logs production app -n all      # Every line
dockflow logs production --since 1h      # Last hour
dockflow logs production app --all-tasks # Include crashed/old instances
dockflow logs production app --pick      # Pick an instance from a list
```

<Callout type="info">
The `--pick` picker lists every instance (running + history) with its current state, index, node, and any error message — useful for inspecting why a specific replica crashed. A multi-replica service prefixes each line with its instance label, unless `--no-prefix` is passed.
</Callout>

### Exec

```bash
dockflow exec <env> <service> [command...]
```

Execute a command inside a running container (default: an interactive shell). Aliases: `bash`, `shell`.
The command's own exit code is propagated as the CLI's exit code (never mapped onto one of Dockflow's
own [exit codes](#exit-codes)), and every argument after the service name is passed through unchanged —
quote a multi-word command as one argument for a shell to see it as intended (`dockflow exec production
app "ls -la"`).

`-u, --user <user>` is **refused on k3s** — the Kubernetes exec API always runs as the container's own
user, with no override (see [Orchestrator Support](#orchestrator-support)).

`exec`, `logs` and `restart` target services of `docker-compose.yml`; for a service of `accessories.yml`
(a database, a cache) use `dockflow accessories exec`, `logs` or `restart`. Naming an accessory here fails
with the command to run instead.

| Option | Description |
|--------|-------------|
| `-s, --server <name>` | Target manager |
| `-u, --user <user>` | Run as the given user (Swarm only) |
| `-w, --workdir <dir>` | Working directory inside the container |
| `--sh` | Use `sh` for the interactive shell instead of `bash` |
| `-e, --env <KEY=VALUE>` | Extra environment variable, repeatable |
| `--pod <instance>` | Instance id from `dockflow ps` |
| `--pick` | Interactively pick the instance |
| `-c, --container <name>` | Container of a multi-container pod (k3s) |
| `-T, --no-tty` | Never allocate a TTY |

```bash
dockflow exec production app bash          # Interactive shell
dockflow exec production app "ls -la"      # Run a command
dockflow bash production app --sh          # `bash` alias, sh instead of bash (Alpine containers)
dockflow exec production db "psql -U user" # Database access (db in docker-compose.yml)
dockflow accessories exec production postgres "psql -U postgres"   # an accessory
```

### Copy

```bash
dockflow cp <env> <src> <dest>
```

Copy files between the local machine and a container, in either direction — exactly one of `<src>`
and `<dest>` must be `<service>:<path>`, the other a local path. Directory copies and Docker's
trailing-`/.` "contents of" convention both work, on either orchestrator.

| Option | Description |
|--------|-------------|
| `-s, --server <name>` | Target manager |
| `--accessories` | Target the accessories role instead of the app |
| `--pod <instance>` | Instance id from `dockflow ps` |
| `--pick` | Interactively pick the instance |
| `-c, --container <name>` | Container of a multi-container pod (k3s) |

```bash
dockflow cp production web:/app/logs ./logs        # Copy out
dockflow cp production ./config.json web:/app/     # Copy in
dockflow cp production web:/app/data/. ./data      # Directory contents, not the directory itself
```

### Restart

```bash
dockflow restart <env> [service]
```

Force restart services (a rolling update with no image change). Waits until the restarted service is
ready again on both orchestrators, unless `--no-wait` is passed. A service already scaled to 0 is
resumed instead of restarted.

| Option | Description |
|--------|-------------|
| `-s, --server <name>` | Target manager |
| `--no-wait` | Do not wait for the restart to complete |

```bash
dockflow restart production           # All services
dockflow restart production app       # Specific service
```

### Stop

```bash
dockflow stop <env>
```

Stop the stack: on Swarm, removes it; on k3s, scales every workload to 0 replicas. On both
orchestrators, volumes, release history and accessories are **kept** — `stop` never deletes data, and a
following `dockflow deploy` brings everything back. Prompts for confirmation unless `-y`.

| Option | Description |
|--------|-------------|
| `-y, --yes` | Skip confirmation |
| `-s, --server <name>` | Target manager |

### Scale

```bash
dockflow scale <env> <service> <replicas>
```

Scale a service to a specified number of replicas. Waits until the new replica count is ready on both
orchestrators, unless `--no-wait`. A `global`/DaemonSet-mode service (one instance per node) cannot be
scaled — its replica count follows the node count instead.

| Option | Description |
|--------|-------------|
| `-s, --server <name>` | Target manager |
| `--no-wait` | Do not wait for the scale to reach its target |

```bash
dockflow scale production app 3      # Scale to 3 replicas
dockflow scale production worker 5   # Scale workers
```

### Rollback

```bash
dockflow rollback <env> [service]
```

Without a service name, rolls back the **whole release** to the previous version (restores the
**app** role's objects only — see [Deployment](/en/deployment#rollback) for what that means for
accessories). With a service name, rolls back that **one service** to its previous live revision
instead, without touching the release record — the two forms use different mechanisms on k3s (a full
release re-apply vs. `kubectl rollout undo`) and are not interchangeable.

| Option | Description |
|--------|-------------|
| `-s, --server <name>` | Target manager |
| `--allow-chart-drift` | Reinstall a Helm release even when its chart bytes changed upstream since it was recorded (full rollback only) |

```bash
dockflow rollback production app     # Rollback one service to its previous revision
dockflow rollback production         # Rollback the whole release
```

### Status

```bash
dockflow status [env]
```

Show deployment status. Without an argument, summarises every environment, and one that cannot be read shows as unavailable; with one, focuses on that environment, and fails with its error and exit code when it cannot be read, so scripts can rely on it. Identical from every manager on k3s — release state, the deploy lock and `status` itself live in the cluster (see [Multi-host](/en/configuration/multi-host)).

```bash
dockflow status               # All environments
dockflow status production    # One environment
```

### History (Audit)

```bash
dockflow history <env>
```

Show the deployment audit log (who deployed what and when). Alias: `audit`.

<Callout type="warning">
  Unlike release state, `history` reads the log files of **one manager** — the first one that answers, printed by the command — never the whole cluster. After a failover it shows only that manager's view; see [Multi-host](/en/configuration/multi-host#what-survives-a-failover) and `dockflow history-sync` below.
</Callout>

| Option | Description |
|--------|-------------|
| `-s, --server <name>` | Target server |
| `-n, --lines <number>` | Number of entries to show (default: 20) |
| `--all` | Show all entries |
| `-j, --json` | Output as JSON |

### History Sync

```bash
dockflow history-sync <env>
```

Sync deployment history across all cluster nodes. Each node records deployments locally, so after a failover — or when a node was unreachable during a deploy — their histories can diverge. This reconciles them.

| Option | Description |
|--------|-------------|
| `--debug` | Enable debug output |

```bash
dockflow history-sync production
```

### Metrics

```bash

```

first manager to the next reachable one, so a stopped first manager does not empty the output.

| Option | Description |
|--------|-------------|

| `--history` | Show deployment history |
| `-n, --lines <number>` | Number of history entries (default: 20) |
| `-j, --json` | Output as JSON |
| `--prune` | Remove old metrics (keep last 1000) |

### SSH

```bash
dockflow ssh <env> [command...]
```

Open an interactive SSH session or execute a command on the server. Works the same on k3s — this opens

| Option | Description |
|--------|-------------|
| `-s, --server <name>` | Target server |

```bash

```

### Prune

```bash
dockflow prune <env>
```

Remove unused resources. On Swarm, every target (images, containers, volumes, networks) is supported.
On k3s, only **images** are — containerd images imported by Dockflow stay pinned regardless, and
`--containers`, `--volumes` and `--networks` are refused with a pointer to the k3s-native equivalent
(see [Orchestrator Support](#orchestrator-support)); without `--all`, pruning k3s images is a
documented no-op, since containerd keeps no dangling images and the kubelet reclaims unused ones under
disk pressure.

| Option | Description |
|--------|-------------|
| `-a, --all` | Remove all unused images, not just dangling ones |
| `--images` | Prune images only |
| `--containers` | Prune containers only (Swarm only) |
| `--volumes` | Prune volumes only (Swarm only — on k3s, delete volumes explicitly with [`dockflow volumes rm`](#volumes-remove)) |
| `--networks` | Prune networks only (Swarm only) |
| `-y, --yes` | Skip confirmation |
| `-s, --server <name>` | Target server |

<Callout type="warning">
  The `--volumes` option (Swarm) permanently deletes data stored in unattached Docker volumes.
</Callout>

```bash
dockflow prune production              # Prune all (with confirmation)
dockflow prune production -y           # Skip confirmation
dockflow prune production --images -a  # All unused images, both orchestrators
```

### Accessories Logs


| Option | Description |

| `-a, --all-tasks` | Include terminated instances / a crashed pod's previous container |
| `--pick` | Interactively pick which instance to follow |
| `-c, --container <name>` | Container of a multi-container pod (k3s) |
| `--no-prefix` | Never prefix lines with the instance label |
| `--raw` | No-op, kept for compatibility |
| `-s, --server <name>` | Target server |

### Accessories Exec

```bash
dockflow accessories exec <env> <service> [command...]
```

Execute a command in an accessory container (default: an interactive shell).

| Option | Description |
|--------|-------------|
| `-u, --user <user>` | Run as the given user (Swarm only) |
| `-w, --workdir <dir>` | Working directory inside the container |
| `-e, --env <KEY=VALUE>` | Extra environment variable, repeatable |
| `--pod <instance>` | Instance id from `dockflow ps` |
| `--pick` | Interactively pick the instance |
| `-c, --container <name>` | Container of a multi-container pod (k3s) |


### Restart Accessories

```bash
dockflow accessories restart <env> [service]
```

| Option | Description |
|--------|-------------|
| `--force` | Force restart even if the service is updating (no-op) |
| `-s, --server <name>` | Target server |

### Stop Accessories

```bash
dockflow accessories stop <env> [service]
```

Scale accessories to 0 replicas (keeps volumes).

<Callout type="warning">
  On k3s, an accessory scaled to 0 with `stop` **stays at 0** across ordinary app deploys — change
  detection skips a redeploy of `accessories.yml` when it hasn't changed, so nothing re-applies the
  replica count (Swarm parity). Bring it back with `accessories restart` or a forced
  `deploy --accessories`.
</Callout>

| Option | Description |
|--------|-------------|
| `-y, --yes` | Skip confirmation |
| `-s, --server <name>` | Target server |

### Remove Accessories

```bash
dockflow accessories remove <env>    # or: dockflow acc rm <env>
```

Remove the accessories stack. On k3s, PersistentVolumeClaims are **never** deleted implicitly — without
`-v, --volumes` the claims survive removal and are re-attached the next time the accessory is deployed.

| Option | Description |
|--------|-------------|
| `-v, --volumes` | Also remove associated volumes (DESTRUCTIVE) |
| `-y, --yes` | Skip confirmation prompt (also skips the typed confirmation below, for CI) |
| `-s, --server <name>` | Target server |

<Callout type="error">
  The `--volumes` flag permanently deletes all data. You will be prompted to type the environment name to confirm, unless `-y`/`--yes` is passed — the only way to skip that typed confirmation.
</Callout>

```bash
dockflow accessories remove production           # Remove stack (keep volumes)
dockflow accessories remove production --volumes # Remove stack AND volumes
dockflow accessories remove production --volumes -y  # Skip prompt and typed confirmation (CI)
```

## Backup Commands

Backup and restore accessory databases. See [Backup & Restore](/en/configuration/backup) for the per-service configuration and the k3s mechanics (helper pods, per-node backup index).

### Create Backup

```bash
dockflow backup create <env> [service]
```

Create a backup of a service or accessory database. Without a service name, backs up every configured accessory.

| Option | Description |
|--------|-------------|
| `-j, --json` | Output backup metadata in JSON format |
| `-s, --server <name>` | Target server (defaults to the first server for the environment) |

```bash
dockflow backup create production            # Every configured accessory
dockflow backup create production postgres   # One service
dockflow bak create production postgres      # `bak` is an alias
```

### List Backups

```bash
dockflow backup list <env> [service]
```

List available backups. Alias: `ls`.

<Callout type="info">
  On k3s the backup index is **per node** — see [Multi-host](/en/configuration/multi-host) and [Backup & Restore](/en/configuration/backup#limitations) for what happens after a failover.
</Callout>

| Option | Description |
|--------|-------------|
| `-j, --json` | Output in JSON format |
| `--node <name>` | Limit to backup files on this server (manager or worker) |
| `-s, --server <name>` | Target server |

```bash
dockflow backup list production
dockflow backup ls production postgres       # `ls` is an alias
```

### Restore Backup

```bash
dockflow backup restore <env> [service]
```

Restore a service or accessory database from a backup. Restores the latest backup unless `--from` is
given — on k3s, without an explicit `--from <id>`, a restore refuses rather than silently picking an
older backup from a different, unreachable node. Refused when the target service runs more than one
replica (R-23): restoring into several replicas at once would race.

| Option | Description |
|--------|-------------|
| `--from <id>` | Backup ID or date prefix (default: latest) |
| `--force-unverified` | Skip archive verification (unverifiable backups only) |
| `-y, --yes` | Skip the confirmation prompt |
| `-s, --server <name>` | Target server |

```bash
dockflow backup restore production postgres
dockflow backup restore production postgres --from 2026-08-29
```

<Callout type="warning">
  Restoring overwrites the current database. You are prompted to confirm unless `--yes` is passed. Every archive is verified against its checksum before anything is wiped, unless `--force-unverified` is passed for one that predates verification.
</Callout>

### Prune Backups

```bash
dockflow backup prune <env> [service]
```

Remove old backups, keeping the most recent N per service.

| Option | Description |
|--------|-------------|
| `--keep <n>` | Number of backups to keep per service (default: `retention_count` from config, or 10) |
| `--node <name>` | Limit to backup files on this server (manager or worker) |
| `-y, --yes` | Skip the confirmation prompt |
| `-s, --server <name>` | Target server |

```bash
dockflow backup prune production --keep 5
```

## Volumes Commands

k3s only — manage PersistentVolumeClaims. See [Volumes & Data](/en/configuration/volumes) for the
reclaim-policy protocol these commands follow, and the data-safety table that applies to every command
in this guide.

### Volumes List

```bash
dockflow volumes list <env>
```

List PersistentVolumeClaims: name, role, the compose volume key, status, capacity, storage class, node
and reclaim policy.

| Option | Description |
|--------|-------------|
| `--role <role>` | Filter by role (`app` or `accessory`) |
| `--system` | Target the Dockflow system namespace |
| `--namespace <ns>` | Target a Helm release namespace of this stack |
| `-j, --json` | Output in JSON format |
| `-s, --server <name>` | Target manager |

### Volumes Remove

```bash
dockflow volumes rm <env> <name...>
```

Delete one or more claims after a typed confirmation, refusing any claim currently mounted by a running
pod. Follows the [reclaim protocol](/en/configuration/volumes#the-reclaim-protocol): volumes are
processed one at a time, and a claim's original reclaim policy is restored if the command stops before
it finished deleting.

<Callout type="warning">
  `-y` skips **both** the prompt and the typed confirmation, for CI. Without `-y`, a non-interactive
  shell refuses rather than proceeding silently. **No API route or UI action ever deletes a volume**,
  with or without a flag — this command is the only way.
</Callout>

| Option | Description |
|--------|-------------|
| `--system` | Target the Dockflow system namespace |
| `--namespace <ns>` | Target a Helm release namespace of this stack |
| `-y, --yes` | Skip confirmation prompt |
| `-s, --server <name>` | Target manager |

```bash
dockflow volumes list production
dockflow volumes list production --role accessory
dockflow volumes rm production old-cache
```

### Initialize Swarm

```bash
dockflow setup swarm <env>
```

Initialize a Docker Swarm cluster for an environment. Joins every server configured in `servers.yml`
(tagged with `<env>`) into the Swarm.

### Initialize / update k3s

```bash
dockflow setup k3s <env>
```

`dockflow setup k3s <env>` is a thin alias of `dockflow setup --orchestrator k3s --env <env>` — both
forms accept every flag below, and both install, upgrade, repair drift in, and verify the **whole**
cluster of the environment, not one node at a time. Re-running it is always safe. See
[Cluster setup](/en/configuration/kubernetes/setup) for the full guide, the pinned versions, and the
security model.

<Callout type="warning">
  **Breaking change.** This connects with a **bootstrap identity** (`--ssh-user`, default `root`, with
  `-k/--key` or `--password`) — never the deploy key the previous `dockflow setup k3s` used. A cluster
  from before this release, or set up by hand, has no Dockflow state and is refused: uninstall it
  first and run this command fresh. There is no migration path.
</Callout>

| Option | Description |
|--------|-------------|
| `--env <env>` | Environment tag in `servers.yml` (equivalent to `setup k3s <env>`) |
| `--ssh-user <user>` | Bootstrap SSH user, root or passwordless sudo (default: `root`) |
| `-k, --key <path>` | Bootstrap SSH private key |
| `--password <password>` | Bootstrap SSH password or key passphrase (prefer the interactive prompt: argv is visible in your process list and shell history) |
| `--dry-run` | Inspect the nodes and print the plan without changing anything |
| `-y, --yes` | Do not ask before restarts and upgrades |
| `--upgrade` | Consent to upgrading k3s to the pinned version |
| `--flannel-backend <backend>` | `vxlan` or `wireguard-native` (new clusters only) |
| `--skip-firewall` | Do not change ufw/firewalld; print the required flows instead |
| `--skip-network-check` | Skip the cross-node pod network check |
| `--skip-reachability-check` | Skip the post-setup check for ports answering from outside the cluster |
| `--insecure-host-key` | Do not verify or record SSH host keys (prints a warning per node) |
| `--require-host-key` | Refuse to connect to a node with no recorded SSH host key |
| `--convert-datastore` | Consent to the one-way SQLite-to-embedded-etcd conversion (adding a second manager to a single-server cluster) |
| `--shared-cluster` | Allow nodes that already serve another Dockflow environment (shared cluster-admin) |
| `--rotate-deploy-token` | Revoke and recreate the deploy identity token |
| `--reset` | Uninstall k3s from the environment (see `--node`, `--delete-volumes`) |
| `--node <key>` | With `--reset`: only this server (repeatable) |
| `--delete-volumes` | With `--reset`: also delete volume data, datastore backups and the cluster token |
| `--confirm <env>` | With `--reset` in a non-interactive session: the environment name, in place of the typed prompt |
| `--dev` | Upload the locally built CLI instead of the release binary |

```bash
dockflow setup k3s production --ssh-user root --key ~/.ssh/bootstrap_ed25519
dockflow setup k3s production --dry-run
dockflow setup k3s production --upgrade -y
dockflow setup k3s production --reset --node worker1
dockflow setup --orchestrator k3s --env production --ssh-user root -k ~/.ssh/bootstrap_ed25519  # equivalent form
```
