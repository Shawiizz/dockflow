# CLI Commands

import { Callout, Tabs } from 'nextra/components'

Dockflow provides a comprehensive CLI for managing deployments and interacting with running services.

## Installation

<Tabs items={['npm (any OS)', 'npx (no install)', 'Linux / macOS', 'Windows']}>
  <Tabs.Tab>
    ```bash
    npm install -g @dockflow-tools/cli@__DOCKFLOW_VERSION__
    dockflow --version
    ```
  </Tabs.Tab>
  <Tabs.Tab>
    Run any command directly without installing:

    ```bash
    npx @dockflow-tools/cli@__DOCKFLOW_VERSION__ <command>
    ```

    <Callout type="info">
      Every command here pins the latest release, `__DOCKFLOW_VERSION__`. Keep a version pinned wherever Dockflow
      runs unattended, CI included, and move it when you choose to.
    </Callout>
  </Tabs.Tab>
  <Tabs.Tab>
    ```bash
    curl -fsSL https://raw.githubusercontent.com/Shawiizz/dockflow/__DOCKFLOW_VERSION__/install.sh | DOCKFLOW_VERSION=__DOCKFLOW_VERSION__ bash
    dockflow --version
    ```
  </Tabs.Tab>
  <Tabs.Tab>
    ```powershell
    $env:DOCKFLOW_VERSION = "__DOCKFLOW_VERSION__"; irm https://raw.githubusercontent.com/Shawiizz/dockflow/__DOCKFLOW_VERSION__/install.ps1 | iex
    dockflow --version
    ```
  </Tabs.Tab>
</Tabs>

The script detects your platform and architecture, downloads the binary, checks it against the release's [checksums](#verified-downloads), and adds it to your PATH.

<Callout type="info">
  The CLI binary is self-contained and requires no external dependencies for most commands.
  Use `dockflow setup` on the target Linux host, or `dockflow setup user@host` from any platform to configure a remote server via SSH.
</Callout>

### Available Binaries

| Binary | Platform | Architecture |
|--------|----------|-------------|
| `dockflow-linux-x64` | Linux | x86_64 |
| `dockflow-linux-arm64` | Linux | ARM64 |
| `dockflow-macos-x64` | macOS | Intel |
| `dockflow-macos-arm64` | macOS | Apple Silicon |
| `dockflow-windows-x64.exe` | Windows | x86_64 |

### Verified Downloads

Each release publishes `SHA256SUMS`, the SHA-256 of its binaries, and every installer refuses a
binary that does not match it: the npm package carries the checksums of its own version,
`install.sh` and `install.ps1` fetch those of the release they install, and
`dockflow setup user@host` checks the binary it downloads on the server.

For a binary downloaded by hand, from the directory holding it and the release's `SHA256SUMS`,
before renaming it:

```bash
grep ' dockflow-linux-x64$' SHA256SUMS | sha256sum --check          # Linux
grep ' dockflow-macos-arm64$' SHA256SUMS | shasum -a 256 --check    # macOS
```

<Callout type="warning">
  `install.sh` and `install.ps1` refuse a release that publishes no `SHA256SUMS`, as the releases
  made before checksums do: download those from the
  [releases page](https://github.com/Shawiizz/dockflow/releases).
</Callout>

## Connection Configuration

App commands require connection strings configured as CI secrets or in `.env.dockflow` for local development:

```bash
# .env.dockflow (for local CLI usage)
PRODUCTION_MAIN_SERVER_CONNECTION=eyJob3N0Ijoi...  # Base64-encoded JSON
STAGING_STAGING_SERVER_CONNECTION=eyJob3N0Ijoi...
```

The connection string is generated by `dockflow setup` and contains:
- `host`: Server IP or hostname
- `port`: SSH port
- `user`: Deployment user
- `privateKey`: SSH private key
- `password`: User password (optional)

<Callout type="info">
  Server names use underscores in secrets. A server named `main_server` in `servers.yml` uses `MAIN_SERVER` in the secret name.
</Callout>

<Callout type="info">
  All commands that accept an `<env>` argument support **prefix matching**: type `pr` instead of `production`, `st` instead of `staging`, etc. If the prefix is ambiguous, Dockflow will list the matching environments.
</Callout>

## Core Commands

### Deploy

```bash
dockflow deploy [env] [version]
```

Deploy the application to the specified environment. In CI, both `env` and `version` are auto-detected from the git tag or branch name. Without a `version` outside CI, the version after the latest deployed one is used (`1.0.0` for the first deploy).

| Option | Description |
|--------|-------------|
| `--only <list>` | Comma-separated list of services to deploy |
| `--skip-build` | Skip the build phase |
| `--force` | Take the deploy lock even when another deploy holds it |
| `--accessories` | Deploy only the accessories (force redeploy). The app and its release history are left alone: no release is written |
| `--all` | Deploy app + force redeploy accessories |
| `--skip-accessories` | Skip accessories check entirely |
| `--no-failover` | Disable multi-manager failover (use first manager only) |
| `-s, --server <name>` | Deploy through this manager, without failover |
| `--dry-run` | Show what would be deployed without executing |
| `--render` | With `--dry-run`, print the Swarm stack that would be sent |
| `--branch <branch>` | Override auto-detected git branch |
| `--debug` | Enable debug output |

<Callout type="info">
  By default, Dockflow checks if `accessories.yml` has changed and automatically deploys accessories when needed. Use `--skip-accessories` to disable this.
</Callout>

With several managers, a deploy goes through the leader, or else the first manager that answers; `--no-failover` uses the first manager only, and `-s, --server` the one you name (also without failover). A deploy takes the [deploy lock](/en/advanced#deployment-locks) and exits with code `51` when another one holds it. Ctrl+C cleans up and releases the lock (exit code `130`).

```bash
dockflow deploy production 1.0.0          # Deploy specific version
dockflow deploy staging                   # Auto-generated version
dockflow deploy production --accessories  # Force redeploy accessories only
dockflow deploy production --all          # Deploy app + accessories
dockflow deploy production --dry-run      # Preview without executing
dockflow deploy production --dry-run --render > stack.yml   # The Swarm stack that would be sent
```

`--dry-run --render` prints, on standard output, the app stack exactly as `dockflow deploy` would send it to `docker stack deploy`: templates rendered, image tags of the version, the `--only` filter applied, Swarm defaults and Traefik labels added, `build` sections removed. Nothing is built, uploaded or deployed, and every other line goes to standard error, so the output can be redirected to a file. It still reads from the manager (the active manager, the latest version when you give none, and under `--only` the tags of the running release). Accessories and Traefik itself are separate stacks and are not printed, and `--render` without `--dry-run` is refused.

<Callout type="warning">
  The stack is printed as it would be sent, so a value rendered from `servers.yml` or a CI secret (`{{ current.env.* }}`) appears in clear. A warning line says so before the YAML. Do not paste the output in a ticket or a CI log without reading it first.
</Callout>

### Build

```bash
dockflow build [env]
```

Build Docker images locally without deploying. In CI, the environment is auto-detected from the git tag or branch name.

| Option | Description |
|--------|-------------|
| `--only <list>` | Comma-separated list of services to build |
| `--push` | Push images to registry after build |
| `--skip-hooks` | Skip pre-build and post-build hooks |
| `--branch <branch>` | Override auto-detected git branch |
| `--debug` | Enable debug output |

```bash

dockflow build production --only app      # Build specific service
dockflow build production --push          # Build and push to registry
```

### Init

```bash
dockflow init
```

Initialize the `.dockflow/` folder structure: `config.yml`, `servers.yml` and `docker/docker-compose.yml`, with the project name taken from the project itself, and `.env.dockflow` added to `.gitignore`. It asks before overwriting an existing `.dockflow/`, then offers to set up CI/CD workflows for GitHub Actions, GitLab CI or Bitbucket Pipelines. The command takes no arguments or options.

### Config

```bash
dockflow config [subcommand]
```

Display and validate project configuration.

| Subcommand | Description |
|------------|-------------|
| `show` (default) | Display current configuration |
| `validate` (alias: `check`) | Validate configuration files against schemas |
| `path` | Show configuration directory path |

Validation also warns about unknown keys: a key the schema does not declare is silently ignored at runtime (typos never fail a deploy), so `validate` flags each one with a "did you mean" suggestion when a close match exists — e.g. `backup.retention` → `Did you mean "retention_count"?`.

| Option | Applies to | Description |
|--------|-----------|-------------|
| `-j, --json` | show, validate | Output as JSON |
| `--verbose` | validate | Show detailed validation output |

```bash
dockflow config                   # Show configuration
dockflow config show --json       # The same, as JSON
dockflow config validate          # Validate config files
dockflow config check             # Same as validate
dockflow config path              # Show config directory
```

### Validate

```bash
dockflow validate [env]
```

Validate `.dockflow` configuration files against their schemas. Runs entirely offline — no SSH connection, no server required — which makes it the fastest way to check a config before pushing.

It checks `config.yml` and `servers.yml` (or `dockflow.yml` in the flat layout), expands the plugins the project uses, looks for the compose file, and reports unknown keys with a "did you mean" suggestion. It also fails on shell-style `$VAR` and `${VAR}` placeholders in the compose and accessories files, which Dockflow does not substitute (see [Docker Compose](/en/configuration/docker-compose)).

| Option | Description |
|--------|-------------|
| `--env <env>` | Also check that a specific environment exists in `servers.yml` |

The environment can be given as an argument or with `--env`; giving two different ones is an error.

```bash
dockflow validate                 # Validate every configuration file
dockflow validate production      # Also check that production exists in servers.yml
dockflow validate --env production
```

Exits `0` when everything is valid, `60` when a check fails.

## App Commands

These commands interact with deployed services via SSH, through a manager of the environment: the leader, or else the first manager that answers, so one manager down does not stop them. Most accept `-s, --server <name>` to name the manager to use (`dockflow ssh` accepts any server, workers included).

### Logs

```bash
dockflow logs <env> [service]
```

View logs from running services. Without a service, every service of the stack is shown. Only **currently running task replicas** are streamed by default — terminated and crashed replicas are excluded to avoid interleaved noise from past failures. Use `--all-tasks` to include them, or `--pick` to select one specific replica interactively (the service too, when none is named).

| Option | Description |
|--------|-------------|
| `-f, --follow` | Follow log output; without a service, every service at once |
| `-n, --tail <lines>` | Number of lines to show, or `all` (default: 100) |
| `-T, --timestamps` | Show timestamps |
| `--since <time>` | Show logs since a duration (`30m`, `1h30m`, `2d`), a date (`2024-01-01`, local midnight), a timestamp (`2024-01-01T10:00:00Z`, local time without a zone) or unix seconds |
| `-s, --server <name>` | Target manager |
| `-a, --all-tasks` | Include logs from terminated/historical task replicas |
| `--pick` | Interactively pick which task replica to show |
| `--no-prefix` | Do not prefix lines with their instance |

When several replicas or services share the output, each line starts with its instance (`web.2 |`), in a colour of its own.

```bash
dockflow logs production                 # All services, running replicas only
dockflow logs production -f              # Follow every service
dockflow logs production app -f          # Follow specific service
dockflow logs production app -n 500      # Last 500 lines
dockflow logs production --since 1h      # Last hour
dockflow logs production app --all-tasks # Include crashed/old replicas
dockflow logs production app --pick      # Pick a replica from a list
```

<Callout type="info">
The `--pick` picker lists every task (running + history) with its current state, replica index, node, and any error message — useful for inspecting why a specific replica crashed.
</Callout>

### Exec

```bash
dockflow exec <env> <service> [command...]
```

Execute a command inside a running container, or open an interactive shell when no command is given (bash when the container has it, else sh). Aliases: `bash`, `shell`, so `dockflow bash production app` opens a shell. A command that is only `bash`, `/bin/bash`, `sh` or `/bin/sh` opens that shell too.

| Option | Description |
|--------|-------------|
| `-s, --server <name>` | Target manager |
| `-u, --user <user>` | Run as specified user |
| `-w, --workdir <dir>` | Working directory inside the container (absolute path) |
| `-e, --env <KEY=VALUE>` | Environment variable for the command, repeatable |
| `--sh` | Use sh instead of bash for the interactive shell (Alpine containers) |
| `--pick` | Choose the task to run in |
| `-T, --no-tty` | Never allocate a TTY |

The command runs inside the container, never on the server: a single argument holding spaces or shell syntax (`"ls | wc -l"`) runs through `sh -c` in the container, several arguments are passed as they are. Output streams back as it comes, stdin is forwarded when piped (`cat dump.sql | dockflow exec production db psql`), a TTY is allocated only when both ends are terminals, and the command's exit code becomes `dockflow`'s.

```bash
dockflow exec production app                         # Interactive shell
dockflow shell production app --sh                  # Interactive sh
dockflow exec production app "ls -la /app | head"    # Shell syntax runs in the container
dockflow exec production db psql -U user             # Several arguments, passed as they are
dockflow exec production app -e DEBUG=1 node task.js # With an environment variable
```

### Cp

```bash
dockflow cp <env> <src> <dest>
```

Copy files between your machine and a container, in either direction. Exactly one side is `<service>:<absolute path>`; the other is a local path. The data is streamed through `docker cp` on the node running the container, so the image does not need a shell or `tar`.

| Option | Description |
|--------|-------------|
| `-s, --server <name>` | Target manager |
| `--accessories` | Copy in an accessory instead of the app |
| `--pick` | Choose the task to copy in |

It follows `docker cp`: a file or directory lands inside an existing destination directory under its own name, at a new name when the destination does not exist (its parent must), and a file overwrites an existing file. A source ending in `/.` copies the contents of the directory instead of the directory, into a destination that exists. A Windows drive such as `C:\data` is a local path, never a service.

Copying out refuses what could escape the destination: absolute or `..` names, links pointing outside it, and anything written through a link. Setuid, setgid and sticky bits are dropped, and devices and FIFOs are skipped with a warning.

```bash
dockflow cp production app:/app/logs ./logs              # Directory out, as ./logs
dockflow cp production app:/app/logs/. ./logs            # Its contents into the existing ./logs
dockflow cp production ./nginx.conf app:/etc/nginx/      # File in
dockflow cp production ./conf/. app:/etc/app             # Contents of ./conf into /etc/app
dockflow cp production redis:/data/dump.rdb . --accessories
```

### Restart

```bash
dockflow restart <env> [service]
```

Force restart services (rolling update). A service scaled to 0 replicas is not started by a restart: the command says so, and `dockflow scale` or `dockflow deploy` gives it replicas.

| Option | Description |
|--------|-------------|
| `-s, --server <name>` | Target manager |
| `--no-wait` | Return once Swarm accepted the change, without waiting for convergence |

```bash
dockflow restart production           # All services
dockflow restart production app       # Specific service
```

### Stop

```bash
dockflow stop <env>
```

Stop and remove the entire stack. Prompts for confirmation, and takes the [deploy lock](/en/advanced#deployment-locks).

| Option | Description |
|--------|-------------|
| `-y, --yes` | Skip confirmation |
| `-s, --server <name>` | Target manager |

### Scale

```bash
dockflow scale <env> <service> <replicas>
```

Scale a service to a specified number of replicas (a non-negative integer). Only replicated services can be scaled: a global service runs one task per node, and a job runs to completion.

`scale`, `restart` and `accessories restart` wait for the services to converge, 300 seconds at most; past that they fail and Swarm keeps trying in the background. `--no-wait` returns at once.

| Option | Description |
|--------|-------------|
| `-s, --server <name>` | Target manager |
| `--no-wait` | Return once Swarm accepted the change, without waiting for convergence |

```bash
dockflow scale production app 3      # Scale to 3 replicas
dockflow scale production worker 5   # Scale workers
```

### Rollback

```bash
dockflow rollback <env> [service]
```

Rollback a service to its previous version, or, without a service, the whole stack to its previous release. It takes the [deploy lock](/en/advanced#deployment-locks) and records the rollback in the audit log. It is not available for upload-only projects (`no_services`): redeploy the commit you want instead.

| Option | Description |
|--------|-------------|
| `-s, --server <name>` | Target manager |

```bash
dockflow rollback production app     # Rollback specific service
dockflow rollback production         # Rollback all services
```

### Status

```bash
dockflow status [env]
```

Show deployment status: the deployed version, how many replicas run out of the wanted ones, and when it was deployed. Without an argument, summarises every environment, each read within 8 seconds and shown as `unavailable` when it cannot be read; with one, focuses on that environment and fails with its error and exit code when it cannot be read.

```bash

```

### History

```bash
dockflow history <env>
```

Show the deployment audit log (who deployed what and when). Alias: `audit`. Every node keeps a copy of the log; the first node that has entries is read, and the command says when it is not the first one. Use [`history-sync`](#history-sync) to reconcile the copies.

| Option | Description |
|--------|-------------|
| `-s, --server <name>` | Target manager |
| `-n, --lines <number>` | Number of entries to show (default: 20) |
| `--all` | Show all entries (up to 1000) |
| `-j, --json` | Output as JSON |

### History Sync

```bash
dockflow history-sync <env>
```

Sync deployment history across all cluster nodes. Each node records deployments locally, so after a failover — or when a node was unreachable during a deploy — their histories can diverge. This reconciles them.

| Option | Description |
|--------|-------------|
| `--debug` | Enable debug output |

```bash
dockflow history-sync production
```

### Metrics

```bash
dockflow metrics <env>
```

Show deployment metrics and statistics: success rate, average duration, activity over the last day, week and month, and the most deployed versions. Metrics are recorded after each deployment and each rollback, and every node keeps a copy: without `--server`, the first node that has some is read, and `--prune` cleans every node.

| Option | Description |
|--------|-------------|
| `-s, --server <name>` | Target manager |
| `--history` | Show deployment history |
| `-n, --lines <number>` | Number of history entries (default: 20) |
| `-j, --json` | Output as JSON |
| `--prune` | Remove old metrics (keep last 1000) |

### SSH

```bash
dockflow ssh <env> [command...]
```

Open an interactive SSH session or execute a command on a server (the first manager by default; `--server` may name any server, workers included). A command's exit code becomes `dockflow`'s.

| Option | Description |
|--------|-------------|
| `-s, --server <name>` | Target server, workers included (default: the first manager) |

### Prune

```bash
dockflow prune <env>
```

Remove unused Docker resources on every node of the environment (images are sent to every node, so old ones pile up on workers too). The nodes are listed before you confirm; a node where pruning fails is named, after every node was tried.

| Option | Description |
|--------|-------------|
| `-a, --all` | Remove all unused images, not just dangling |
| `--images` | Prune images only |
| `--containers` | Prune containers only |
| `--volumes` | Prune volumes only |
| `--networks` | Prune networks only |
| `-y, --yes` | Skip confirmation |
| `-s, --server <name>` | Target manager |

<Callout type="warning">
  The `--volumes` option permanently deletes data stored in unattached Docker volumes.
</Callout>

```bash
dockflow prune production              # Prune all (with confirmation)
dockflow prune production -y           # Skip confirmation
dockflow prune production --images -a  # All unused images
```

## Lock Commands

Manage deployment locks to prevent concurrent deployments. A lock is a file on the manager; `deploy`, `rollback`, `stop`, `accessories remove` and `backup restore` take it themselves while they run (see [Deployment Locks](/en/advanced#deployment-locks)).

### Acquire Lock

```bash
dockflow lock acquire <env>
```

Lock the environment by hand, for maintenance for instance. Fails with exit code `51` when it is already locked and `--force` is not given.

| Option | Description |
|--------|-------------|
| `-s, --server <name>` | Target manager |
| `-m, --message <message>` | Lock reason |
| `--force` | Force acquire even if already locked |

### Lock Status

```bash
dockflow lock status <env>
```

Show who holds the lock, since when, and whether it is stale (older than the [configured threshold](/en/configuration/config-file#deploy-lock)).

| Option | Description |
|--------|-------------|
| `-s, --server <name>` | Target manager |

### Release Lock

```bash
dockflow lock release <env>
```

Remove the lock, whoever holds it. Nothing is asked: the holder is printed, then the lock removed.

| Option | Description |
|--------|-------------|
| `-s, --server <name>` | Target manager |

### Restart Accessories

```bash

```

Force a rolling restart. An accessory stopped with `accessories stop` is not started by it: use `dockflow deploy <env> --accessories`.

| Option | Description |
|--------|-------------|
| `--force` | Force restart even if updating |
| `-s, --server <name>` | Target manager |
| `--no-wait` | Return once Swarm accepted the change, without waiting for convergence |

### Stop Accessories

```bash
dockflow accessories stop <env> [service]
```

Scale accessories to 0 replicas (keeps volumes). `dockflow deploy <env> --accessories` starts them again; `restart` does not.

| Option | Description |
|--------|-------------|
| `-y, --yes` | Skip confirmation |
| `-s, --server <name>` | Target manager |
| `--no-wait` | Return once Swarm accepted the change, without waiting for the accessories to stop |

### Remove Accessories

```bash
dockflow accessories remove <env>    # or: dockflow acc rm <env>
```

Remove the accessories stack entirely. Volumes are kept unless `--volumes` is given. It takes the [deploy lock](/en/advanced#deployment-locks).

| Option | Description |
|--------|-------------|
| `-v, --volumes` | Also remove volumes (DESTRUCTIVE) |
| `-y, --yes` | Skip confirmation |
| `-s, --server <name>` | Target manager |

<Callout type="error">
  The `--volumes` flag permanently deletes all data. You are prompted to type the environment name to confirm. `-y, --yes` skips that prompt too, as it skips every confirmation, so use it in scripts only when the volumes must go.
</Callout>

```bash
dockflow accessories remove production                    # Keep the volumes
dockflow accessories remove production --volumes          # Type "production" to confirm
dockflow accessories remove production --volumes --yes    # No prompt, for CI
```

## Backup Commands

Backup and restore accessory databases. See [Backup & Restore](/en/configuration/backup) for the per-service configuration.

### Create Backup

```bash
dockflow backup create <env> [service]
```

Create a backup of a service or accessory database. The service is required and must be configured under `backup` (the error lists the available ones).

| Option | Description |
|--------|-------------|
| `-j, --json` | Output backup metadata in JSON format |
| `-s, --server <name>` | Target server (defaults to the first server for the environment) |

```bash
dockflow backup create production postgres   # One service
dockflow bak create production postgres      # `bak` is an alias
```

### List Backups

```bash
dockflow backup list <env> [service]
```

List available backups of one service, or of every configured one. Backups are stored on the servers of the environment, and a server that does not answer is named, its backups missing from the list.

| Option | Description |
|--------|-------------|
| `-j, --json` | Output in JSON format |
| `--node <name>` | Only the backups stored on this server |
| `-s, --server <name>` | Target manager |

```bash
dockflow backup list production
dockflow backup ls production postgres       # `ls` is an alias
```

### Restore Backup

```bash
dockflow backup restore <env> [service]
```

Restore a service or accessory database from a backup. The service is required. Restores the latest backup unless `--from` is given, and takes the [deploy lock](/en/advanced#deployment-locks) so that a deploy cannot replace the service meanwhile. A service that runs more than one replica is refused before the confirmation (exit code 72), because the restore would reach one replica only: scale it to 1, restore, then scale it back.

| Option | Description |
|--------|-------------|
| `--from <id>` | Backup ID or date prefix (default: latest) |
| `--force-unverified` | Restore a dump whose integrity marker is missing, once you have checked it yourself (see [Verification](/en/configuration/backup#verification)) |
| `-y, --yes` | Skip the confirmation prompt |
| `-s, --server <name>` | Target manager |

```bash
dockflow backup restore production postgres
dockflow backup restore production postgres --from 2026-08-29
```

<Callout type="warning">
  Restoring overwrites the current data (the volumes, for a volume backup). You are prompted to type the environment name to confirm unless `--yes` is passed.
</Callout>

### Prune Backups

```bash
dockflow backup prune <env> [service]
```

Remove old backups, keeping the most recent N per service, for one service or all of them.

| Option | Description |
|--------|-------------|
| `--keep <n>` | Number of backups to keep per service (default: `retention_count` from config, or 10) |
| `-y, --yes` | Skip the confirmation prompt |
| `--node <name>` | Only the backups stored on this server |
| `-s, --server <name>` | Target manager |

```bash
dockflow backup prune production --keep 5
```

## Setup Commands

Configure servers for deployment. Must be run on a Linux host, or use `setup user@host` for remote servers.

### Interactive Setup

```bash
dockflow setup
```

Run the interactive setup wizard. On Windows/macOS, prompts to connect to a Linux server via SSH.

### Remote Setup

```bash
dockflow setup user@host[:port]
```

Run setup on a remote Linux server from any platform. The server must be x86_64 (amd64) or
aarch64 (arm64); any other architecture is refused before anything is put on it.

The Dockflow binary is placed in a private temporary directory on the server (created with
`mktemp -d`, readable by the connecting user only), checked, run from there and removed when
setup ends, whether it succeeded or not.

| Option | Description |
|--------|-------------|
| `-k, --key <path>` | Path to SSH private key |
| `--password <password>` | SSH password |
| `--connection <string>` | Use existing Dockflow connection string |
| `--dev` | Build the CLI from a Dockflow source checkout and upload it instead of downloading the release (for working on Dockflow itself) |

```bash
dockflow setup root@192.168.1.10 -k ~/.ssh/id_ed25519
dockflow setup root@192.168.1.10:2222 -k ~/.ssh/id_ed25519
dockflow setup --connection "eyJob3N0Ijoi..."
```

### Non-Interactive Setup

```bash
dockflow setup --host <ip> --user <name> --password <pwd> --generate-key
```

Configure a server without prompts (Linux only, must run on target host). Pass flags directly instead of using the interactive wizard.

| Option | Description |
|--------|-------------|
| `--host <host>` | Public IP/hostname for connection string |
| `--port <port>` | SSH port (default: 22) |
| `--user <user>` | Deployment username |
| `--password <password>` | Password for the new deploy user |
| `--password-file <path>` | Read that password from a file instead of the command line, where other users of the machine could see it in the process list |
| `--ssh-key <path>` | Path to existing SSH private key |
| `--generate-key` | Generate new SSH key |
| `--deploy-password <pw>` | Password for the deploy user created remotely (remote, with `--user`); sent to the server through a file in the private directory, not on a command line |
| `--skip-docker-install` | Skip Docker installation |
| `--nginx` | Install nginx, for the [nginx plugin](/en/configuration/plugins#nginx) |
| `--no-port-filter` | Let the internet reach every published container port, instead of only the [public ports](/en/configuration/firewall) |
| `-y, --yes` | Skip confirmations |

### Initialize Swarm

```bash
dockflow setup swarm <env>
```

Initialize a Docker Swarm cluster for an environment. Joins all servers configured in `servers.yml` into the Swarm. It exits with an error, naming them, when a worker could not be joined or a node is not `Ready` within a minute; running it again leaves the nodes already in the cluster alone.

### Check Dependencies

```bash
dockflow setup check
```

Verify all required dependencies are installed.

### Get Connection String

```bash
dockflow setup connection
```

Display connection string for an existing deployment user.

| Option | Description |
|--------|-------------|
| `--host <host>` | Server IP/hostname |
| `--port <port>` | SSH port (default: 22) |
| `--user <user>` | Deployment username |
| `--key <path>` | Path to SSH private key |

## Exit Codes

A failed command prints its error, with a suggestion when there is one, and exits with a code that tells the failure apart, so scripts and CI can react to it.

| Code | Meaning |
|------|---------|
| `0` | Success |
| `1` | Unexpected error |
| `3` | A command run on the server failed |
| `10` | `config.yml` not found |
| `11` | Configuration invalid |
| `12` | `servers.yml` not found |
| `21` | No server for the environment, or an environment prefix matching several |
| `30` | Connection to a server failed |
| `31` | No connection string or SSH key for a server |
| `32` | A server refused the SSH key or user. Re-run `dockflow setup` on the server, then update the connection string |
| `40` | Docker is not installed or not running on the server |
| `41` | Stack not found |
| `42` | Service not found |
| `43` | No container or task found for the service |
| `50` | Deploy failed |
| `51` | Deploy locked: another deploy, or a lock taken by hand, holds the [lock](/en/advanced#deployment-locks) |
| `52` | Rollback failed |
| `53` | Health check failed |
| `60` | Validation failed, or the command does not apply to this project |
| `61` | Invalid argument |
| `70` | Backup failed |
| `71` | Backup not found |
| `72` | Restore failed |
| `73` | No backup configuration for the service |
| `130` | Interrupted with Ctrl+C |
| `143` | Terminated by SIGTERM, when the command had nothing to clean up |

`dockflow exec`, `dockflow accessories exec` and `dockflow ssh` with a command exit with the code of that command, whatever it is. A command interrupted with Ctrl+C while it holds the deploy lock cleans up first and exits with `130`; a second Ctrl+C exits at once.

## Requirements

- `.env.dockflow` with connection strings (or CI secrets)
- `.dockflow/config.yml` with `project_name`

**For setup commands (on target Linux host):**
- Root access (local setup must run as root; remote setup escalates automatically)
- SSH (`ssh`, `ssh-keygen`)
- curl (downloads the Docker install script)
- sudo (the deploy user records public ports and reloads nginx through it)

Missing dependencies are installed automatically during setup.

## Full Workflow Example

```bash
# 1. Setup server
dockflow setup root@192.168.1.10 -k ~/.ssh/id_ed25519

# 2. Save connection string
echo "PRODUCTION_MAIN_SERVER_CONNECTION=..." > .env.dockflow

# 3. Initialize project
dockflow init

# 4. Validate configuration
dockflow config validate

# 5. Build locally (optional)
dockflow build production

# 6. Deploy
dockflow deploy production 1.0.0

# 7. Monitor
dockflow logs production -f
dockflow details production
dockflow ps production

# 8. Check version and history
dockflow version production
dockflow history production

# 9. Troubleshoot
dockflow diagnose production
dockflow exec production app
dockflow ssh production

# 10. Scale
dockflow scale production app 3

# 11. Rollback if needed
dockflow rollback production app

# 12. Manage accessories
dockflow acc logs production postgres -f
dockflow acc exec production postgres psql

# 13. Cleanup
dockflow prune production --images -a
```
