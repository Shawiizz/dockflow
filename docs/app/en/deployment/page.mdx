# Deployment

import { Callout, Steps, Tabs } from 'nextra/components'

When you run `dockflow deploy`, Dockflow builds your images, transfers them to your server, deploys the stack, and verifies that services are healthy. The process adapts automatically based on your [`orchestrator`](/en/configuration/orchestrator) setting (Swarm or k3s).

## Triggering a Deployment

<Tabs items={['CLI', 'Tag (CI/CD)', 'Branch (CI/CD)']}>
  <Tabs.Tab>
    ```bash
    dockflow deploy production 1.0.0
    ```
  </Tabs.Tab>
  <Tabs.Tab>
    Push a git tag to trigger a deployment. The CLI auto-detects the environment from the tag suffix:

    ```bash
    git tag 1.0.0              # → deploys to production
    git tag 1.0.0-staging      # → deploys to staging
    git push origin --tags
    ```

    The tag name is used as the version. A tag without a suffix (e.g., `1.0.0`) deploys to `production`. A tag ending with `-<env>` (e.g., `1.0.0-staging`) deploys to that environment.
  </Tabs.Tab>
  <Tabs.Tab>
    Push to a branch to trigger a build or deploy. The CLI auto-detects the branch and generates a version from `<branch>-<commit-sha>`:

    ```bash
    git push origin main       # → builds or deploys to production as main-abc12345
    ```
  </Tabs.Tab>
</Tabs>

The environment name must match a server tag in your [`servers.yml`](/en/configuration/servers).

## Deployment Process

<Steps>
### Image Transfer

Dockflow transfers your images to the server via SSH. The method depends on your orchestrator and [container engine](/en/configuration/container-engine):

<Tabs items={['Swarm (Docker)', 'Swarm (Podman)', 'k3s']}>
  <Tabs.Tab>
```
docker save image:tag | gzip -1 | ssh user@host "gunzip | docker load"
```
  </Tabs.Tab>
  <Tabs.Tab>
```
podman save image:tag | gzip -1 | ssh user@host "gunzip | podman load"
```
  </Tabs.Tab>
  <Tabs.Tab>
```
docker save image:tag | gzip -1 | ssh user@host "gunzip | sudo k3s ctr -n k8s.io images import -"
```
k3s always uses containerd for image import, regardless of the build engine.
  </Tabs.Tab>
</Tabs>

No external registry required. For multi-node Swarm clusters, images are streamed to each node. You can optionally configure a [Docker registry](/en/configuration/registry) for faster transfers.

### Stack Deployment

<Tabs items={['Swarm', 'k3s']}>
  <Tabs.Tab>
Your application is deployed as a Swarm stack:

```
docker stack deploy -c docker-compose.yml my-app-production
```
  </Tabs.Tab>
  <Tabs.Tab>
Dockflow **renders** your `docker-compose.yml` (and `accessories.yml`) into Kubernetes objects — pure,
offline, in the CLI itself — then **server-side applies** them with a three-way strategic merge, the
same mechanism `kubectl apply` uses, so a field an operator or another controller manages by hand is
never overwritten by a stale one Dockflow no longer sets:

```
kubectl apply --server-side -f - (Deployments/StatefulSets, Services, PVCs, IngressRoutes, Secrets, ConfigMaps)
```

Each compose service becomes a workload (a Deployment, or a StatefulSet for `x-dockflow.kind:
statefulset`) plus a ClusterIP Service, inside a `dockflow-{project}-{env}` namespace. Convergence is
then watched **fail-fast**: the first pod failure that cannot self-resolve (`CrashLoopBackOff`,
`ImagePullBackOff`, a scheduling failure, ...) ends the wait immediately rather than exhausting the full
timeout window, so a broken deploy is reported in seconds, not minutes.
  </Tabs.Tab>
</Tabs>

Each deployment creates a new release record — a directory on the server (Swarm) or a Secret in the
cluster (k3s, see [below](#releases-stored-in-the-cluster-k3s)).

### Health Verification

After deployment, Dockflow verifies:

1. **Internal checks**: Swarm reports services as healthy / k3s pods converge fail-fast to Ready with no restart-count regression
2. The correct image version is running
3. External health check endpoints respond (if [configured](/en/configuration/config-file#health-checks))

### Rollback on Failure

<Tabs items={['Swarm', 'k3s']}>
  <Tabs.Tab>
If health checks fail, Dockflow:

1. Detects the rollback via Swarm status
2. Waits for the previous version to stabilize
3. Cleans up the failed release
4. Reports the deployment as failed
  </Tabs.Tab>
  <Tabs.Tab>
If convergence or a health check fails, Dockflow's **automatic revert** re-applies the previous
release's objects (workloads, Services, routes) — deliberately more than a bare `kubectl rollout undo`,
which restores only a workload's pod template and would leave a Service or route at its new,
possibly-broken version. PersistentVolumeClaims are never re-applied by a revert. A workload that has
no previous release artifact to restore falls back to `rollout undo --to-revision=<n>`. A **first**
deploy that fails leaves the workloads in place for debugging instead of deleting them — there is
nothing to revert to yet.
  </Tabs.Tab>
</Tabs>
</Steps>

## Releases Stored in the Cluster (k3s)

On k3s, release history and the deploy lock live in the cluster itself — a Secret per release plus a
Lease — not in files on one manager. Every manager therefore sees the identical release state and lock
status (see [Multi-host](/en/configuration/multi-host) for the two things that are *not* cluster-wide:
`history`/`audit`/`metrics` and backups).

<Callout type="info">
  **A release stays recorded even when the deploy fails after the app was applied** — a failing HTTP
  check, a fatal post-deploy hook, or an apply whose outcome could not be confirmed. The cluster really
  is running that version, so `dockflow status` reports it rather than pointing at stale state; the CLI
  prints `Release 1.4.2 is deployed but the deploy reported a failure; current stays 1.4.2`. Nothing
  removes the release record on this path — only a confirmed automatic revert does that.
</Callout>

## Rollback

`dockflow rollback <env>` (no service name) rolls back the **whole release** — but on k3s it
restores the **app** role only: accessories are never rolled back automatically, because re-applying
an older accessory definition (a downgraded database image against data a newer version already
migrated) is the one rollback step that can destroy data. When the app and accessories have drifted
apart because of this, the command **warns and names the accessories still running the newer
definition**, so the operator can decide by hand rather than have Dockflow guess.

`dockflow rollback <env> <service>` rolls back **one service** to its previous live revision instead
(`kubectl rollout undo` under the hood on k3s), without touching the release record at all — see the
[CLI reference](/en/cli#rollback) for the full option list.

## Release Management

Dockflow organizes releases on your server:

```
/var/lib/dockflow/stacks/my-app-production/
├── 1.0.0/
│   └── docker-compose.yml
├── 1.0.1/
│   └── docker-compose.yml
├── 1.0.2/
│   └── docker-compose.yml
└── current -> 1.0.2/
```

The `current` symlink points to the active release. By default, Dockflow keeps the last 3 releases (configurable via [`keep_releases`](/en/configuration/config-file#keep_releases)).

## Health Checks

### Container Health Checks

Define health checks in your `docker-compose.yml`:

```yaml
services:
  app:
    image: my-app
    healthcheck:
      test: ["CMD", "curl", "-f", "http://localhost:3000/health"]
      interval: 10s
      timeout: 5s
      retries: 3
      start_period: 30s
```

- **Swarm**: Docker monitors these checks natively and triggers automatic rollback if containers become unhealthy.
- **k3s**: Dockflow converts them to Kubernetes `livenessProbe` and `readinessProbe` automatically. No manual K8s YAML needed.

### External Health Checks

Configure additional HTTP checks in `.dockflow/config.yml`:

```yaml
health_checks:
  enabled: true
  startup_delay: 15
  on_failure: rollback
  endpoints:
    - name: "API"
      url: "http://localhost:3000/health"
      expected_status: 200
      timeout: 30
      retries: 3
```

See [Health Checks configuration](/en/configuration/config-file#health-checks) for all options.

## Rolling Updates

<Callout type="info">
  Rolling update settings apply to **Swarm only**. For k3s, Kubernetes handles rolling updates via its own Deployment strategy (default: `RollingUpdate` with 25% maxSurge / 25% maxUnavailable).
</Callout>

Dockflow injects safe defaults for zero-downtime Swarm deployments. These are **only applied** if not already defined in your `docker-compose.yml`.

### Default Settings

| Setting | Update | Rollback |
|---------|--------|----------|
| `parallelism` | 1 | 1 |
| `delay` | 10s | 5s |
| `failure_action` | rollback | — |
| `monitor` | 30s | 15s |
| `order` | start-first | start-first |
| `max_failure_ratio` | 0 | — |

<Callout type="info">
Your `docker-compose.yml` values always take precedence. Dockflow only fills in missing fields.
</Callout>

### Customizing

Override any setting in your `docker-compose.yml`:

```yaml
services:
  app:
    deploy:
      replicas: 3
      update_config:
        parallelism: 2
        delay: 5s
        failure_action: pause
        monitor: 60s
        order: stop-first
      rollback_config:
        parallelism: 2
        delay: 3s
```

### Update Order

- **`start-first`** (default): New container starts before the old one stops. Zero downtime, but requires brief extra resources.
- **`stop-first`**: Old container stops before the new one starts. Less resources but causes brief downtime.

For zero-downtime deployments, use `start-first` with at least 2 replicas.

## Manual Operations

<Tabs items={['Swarm', 'k3s']}>
  <Tabs.Tab>
```bash
# View stack status
docker stack services my-app-production

# View service logs
docker service logs my-app-production_app

# Force redeployment
docker service update --force my-app-production_app

# Manual rollback
docker service rollback my-app-production_app

# Remove stack
docker stack rm my-app-production
```
  </Tabs.Tab>
  <Tabs.Tab>
`dockflow setup k3s` writes a **sudo-free** kubeconfig for the deploy identity at
`/var/lib/dockflow/kube/config` on every manager — plain `kubectl`, no `sudo` needed, works the moment
setup finishes:

```bash
# View workloads
KUBECONFIG=/var/lib/dockflow/kube/config kubectl get deployments,statefulsets -n dockflow-my-app-production

# View pods
KUBECONFIG=/var/lib/dockflow/kube/config kubectl get pods -n dockflow-my-app-production

# View service logs
KUBECONFIG=/var/lib/dockflow/kube/config kubectl logs -n dockflow-my-app-production -l app.kubernetes.io/name=web

# Scale a deployment
KUBECONFIG=/var/lib/dockflow/kube/config kubectl scale deployment/web --replicas=3 -n dockflow-my-app-production

# Roll back one workload's pod template only (prefer `dockflow rollback`, which also restores Services and routes)
KUBECONFIG=/var/lib/dockflow/kube/config kubectl rollout undo deployment/web -n dockflow-my-app-production

# Remove everything, including PersistentVolumeClaims (prefer `dockflow stop`, which keeps volumes)
KUBECONFIG=/var/lib/dockflow/kube/config kubectl delete namespace dockflow-my-app-production
```

Prefer the `dockflow` commands above them where one exists — they update the release record and respect
the data-safety rules of [Volumes & Data](/en/configuration/volumes); raw `kubectl` does not.
  </Tabs.Tab>
</Tabs>

## Troubleshooting

### Deployment Stuck

<Tabs items={['Swarm', 'k3s']}>
  <Tabs.Tab>
```bash
docker service ps my-app-production_app --no-trunc
```

Look for error messages in the task output.
  </Tabs.Tab>
  <Tabs.Tab>
```bash
dockflow diagnose production
KUBECONFIG=/var/lib/dockflow/kube/config kubectl get events -n dockflow-my-app-production --sort-by='.lastTimestamp'
```

`dockflow diagnose` groups the failure by its stable **reason**, the same one a failed convergence
reports:

| Reason | What it means |
|---|---|
| `CrashLoopBackOff`, `ContainerRestarted` | The container starts and exits repeatedly — check the app's own logs |
| `ImagePullBackOff`, `ErrImagePull`, `ErrImageNeverPull`, `InvalidImageName` | The image could not be pulled or imported — check the registry, the pull secret, or that a local image was actually imported to every node |
| `CreateContainerConfigError`, `CreateContainerError`, `RunContainerError` | A config problem the kubelet can see (a missing Secret key, an invalid security context, …) |
| `OOMKilled` | The container exceeded its memory limit |
| `Unschedulable`, `ReplicaFailure` | No node currently satisfies the pod's requests, node selector or tolerations |
| `ProgressDeadlineExceeded` | The rollout did not finish within `progressDeadlineSeconds` |
| `PvcPending` | A PersistentVolumeClaim never bound — check the storage class and node capacity |
| `LoadBalancerPending` | A published-port Service never got a ServiceLB address, usually because another Service already holds that host port cluster-wide — the message names the conflicting Service and namespace |
| `Paused`, `WorkloadDeleting` | The workload is mid-rollout-pause, or a previous delete has not finished yet |
| `Timeout`, `TaskFailed`, `HelmFailed` | The wait itself timed out, a one-shot Job failed, or a Helm release failed to become ready |
  </Tabs.Tab>
</Tabs>

### Rollback Loop

If services keep rolling back, the issue is usually in your container health check. Verify the health check command works:

```bash
# Swarm
docker exec <container_id> curl -f http://localhost:3000/health

# k3s
kubectl exec -n dockflow-my-app-production <pod_name> -- curl -f http://localhost:3000/health
```

### Images Not Found

If the orchestrator cannot find images after a rollback, cleanup may have removed them. Redeploy:

```bash
dockflow deploy production 1.0.3
```
