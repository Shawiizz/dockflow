# Deployment

import { Callout, Steps, Tabs } from 'nextra/components'

When you run `dockflow deploy`, Dockflow builds your images, transfers them to your server, deploys the stack to Docker Swarm, and verifies that services are healthy.

## Triggering a Deployment

<Tabs items={['CLI', 'Tag (CI/CD)', 'Branch (CI/CD)']}>
  <Tabs.Tab>
    ```bash
    dockflow deploy production 1.0.0
    ```
  </Tabs.Tab>
  <Tabs.Tab>
    Push a git tag to trigger a deployment. The CLI auto-detects the environment from the tag suffix:

    ```bash
    git tag 1.0.0              # → deploys to production
    git tag 1.0.0-staging      # → deploys to staging
    git push origin --tags
    ```

    The tag name is used as the version. A tag without a suffix (e.g., `1.0.0`) deploys to `production`. A tag ending with `-<env>` (e.g., `1.0.0-staging`) deploys to that environment.
  </Tabs.Tab>
  <Tabs.Tab>
    Push to a branch to trigger a build or deploy. The CLI auto-detects the branch and generates a version from `<branch>-<commit-sha>`:

    ```bash
    git push origin main       # → builds or deploys to production as main-abc12345
    ```
  </Tabs.Tab>
</Tabs>

The environment name must match a server tag in your [`servers.yml`](/en/configuration/servers).

## Deployment Process

<Steps>
### Image Transfer

Dockflow transfers your images to the server via SSH. The method depends on your [container engine](/en/configuration/container-engine):

<Tabs items={['Docker', 'Podman']}>
  <Tabs.Tab>
```
docker save image:tag | gzip -1 | ssh user@host "gunzip | docker load"
```
  </Tabs.Tab>
  <Tabs.Tab>
```
podman save image:tag | gzip -1 | ssh user@host "gunzip | podman load"
```
  </Tabs.Tab>
</Tabs>

No external registry required. For multi-node Swarm clusters, images are streamed to each node. You can optionally configure a [Docker registry](/en/configuration/registry) for faster transfers.

### Stack Deployment

Your application is deployed as a Swarm stack:

```
docker stack deploy -c docker-compose.yml my-app-production
```

Each deployment creates a new release directory on the server.

### Health Verification

After deployment, Dockflow verifies:

1. **Internal checks**: Swarm reports services as healthy
2. The correct image version is running
3. External health check endpoints respond (if [configured](/en/configuration/config-file#health-checks))

### Rollback on Failure

Dockflow waits up to 300 seconds for the services to converge, but gives up as soon as a service's
tasks have failed 10 times since the deploy started: a crash loop does not get better by waiting.

Once the stack reached Swarm, any failure (services that do not converge, a failed internal check,
a failed HTTP check) makes Dockflow, by default (`on_failure: rollback`):

1. Send the previous release's stack to Swarm again
2. Wait for it to converge and run the health checks again
3. Report the deployment as failed, naming the version it went back to

With another [`on_failure`](/en/configuration/config-file#on_failure), nothing is rolled back: the
new version is what runs, so it stays the current release and the command says so. Only when
Swarm put the previous version back by itself is the failed release forgotten.
</Steps>

## Release Management

Dockflow organizes releases on your server:

```
/var/lib/dockflow/stacks/my-app-production/
├── 1.0.0/
│   ├── docker-compose.yml
│   ├── stack.yml
│   └── metadata.json
├── 1.0.1/
├── 1.0.2/
└── current -> 1.0.2/
```

The `current` symlink points to the active release, and `stack.yml` is the rendered stack a rollback re-applies. Release files contain your secrets, so only the deploy user can read them. By default, Dockflow keeps the last 3 releases, and always the current one (configurable via [`keep_releases`](/en/configuration/config-file#keep_releases)).

`dockflow rollback <env>` goes back to the release before `current`; running it again goes one release further back.

## Health Checks

### Container Health Checks

Define health checks in your `docker-compose.yml`:

```yaml
services:
  app:
    image: my-app
    healthcheck:
      test: ["CMD", "curl", "-f", "http://localhost:3000/health"]
      interval: 10s
      timeout: 5s
      retries: 3
      start_period: 30s
```

Docker monitors these checks natively, and Swarm rolls back automatically if containers become unhealthy.

### External Health Checks

Configure additional HTTP checks in `.dockflow/config.yml`:

```yaml
health_checks:
  enabled: true
  startup_delay: 15
  on_failure: rollback
  endpoints:
    - name: "API"
      url: "http://localhost:3000/health"
      expected_status: 200
      timeout: 30
      retries: 3
```

See [Health Checks configuration](/en/configuration/config-file#health-checks) for all options.

## Rolling Updates

Dockflow injects safe defaults for zero-downtime Swarm deployments. These are **only applied** if not already defined in your `docker-compose.yml`.

### Default Settings

| Setting | Update | Rollback |
|---------|--------|----------|
| `parallelism` | 1 | 1 |
| `delay` | 10s | 5s |
| `failure_action` | rollback | — |
| `monitor` | 30s | 15s |
| `order` | start-first | start-first |
| `max_failure_ratio` | 0 | — |

<Callout type="info">
Your `docker-compose.yml` values always take precedence. Dockflow only fills in missing fields.
</Callout>

### Customizing

Override any setting in your `docker-compose.yml`:

```yaml
services:
  app:
    deploy:
      replicas: 3
      update_config:
        parallelism: 2
        delay: 5s
        failure_action: pause
        monitor: 60s
        order: stop-first
      rollback_config:
        parallelism: 2
        delay: 3s
```

### Update Order

- **`start-first`** (default): New container starts before the old one stops. Zero downtime, but requires brief extra resources.
- **`stop-first`**: Old container stops before the new one starts. Less resources but causes brief downtime.

For zero-downtime deployments, use `start-first` with at least 2 replicas.

## Manual Operations

```bash
# View stack status
docker stack services my-app-production

# View service logs
docker service logs my-app-production_app

# Force redeployment
docker service update --force my-app-production_app

# Manual rollback
docker service rollback my-app-production_app

# Remove stack
docker stack rm my-app-production
```

## Troubleshooting

### Deployment Stuck

```bash
docker service ps my-app-production_app --no-trunc
```

Look for error messages in the task output.

### Rollback Loop

If services keep rolling back, the issue is usually in your container health check. Verify the health check command works:

```bash
docker exec <container_id> curl -f http://localhost:3000/health
```

### Images Not Found

If Swarm cannot find images after a rollback, cleanup may have removed them. Redeploy:

```bash
dockflow deploy production 1.0.3
```
