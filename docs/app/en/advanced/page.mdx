# Advanced Usage

Operational patterns for managing deployments beyond the basics.

## Deployment Locks

Prevent concurrent deployments with manual locks:

```bash
# Lock an environment (e.g., during maintenance)
dockflow lock acquire production -m "Database migration in progress"

# Check lock status
dockflow lock status production

# Release when done
dockflow lock release production
```

The `dockflow deploy --force` flag overrides locks when needed.

<Callout type="info">
  Locks also apply automatically during deployments and expire after the [configured threshold](/en/configuration/config-file#deploy-lock).
</Callout>

The commands that change the stack take the same lock: `deploy`, `rollback`, `stop`, `accessories remove` and `backup restore` (the web UI's rollback and restore too). A second one started meanwhile fails with exit code 51 (deploy locked); a manager that does not answer fails with its own code, so a retry loop can tell the two apart. A lock older than the threshold is taken over, and the command says whose lock it was. A running command renews its lock every third of the threshold, so a long deploy is never taken for a dead one; and a command whose lock was taken over leaves the new holder's lock in place when it ends. `dockflow lock release` removes the lock whoever holds it. With several managers, the lock lives on the first manager of `servers.yml` that answers, whichever manager leads the cluster, so every command meets the same lock.

Ctrl+C during one of these commands cleans up and releases the lock, then exits with code 130. A deploy rolls back its uploads and release record; if the new version had already been sent to Swarm, it says so and points to `dockflow status`. `rollback`, `stop`, `accessories remove` and `backup restore` stop at their next safe point instead of dying mid-change. A second Ctrl+C exits at once and leaves the lock until it expires or `dockflow lock release` removes it.

## Selective Deployment

Deploy specific services without affecting others:

```bash
dockflow deploy production --only backend
dockflow deploy production --only frontend,worker
```

Skip the build phase to redeploy with existing images:

```bash
dockflow deploy production --skip-build
```

Preview what a deployment would do without executing:

```bash
dockflow deploy production --dry-run
```

## Debug Workflow

When something goes wrong:

```bash
# 1. Check what's running
dockflow ps production
dockflow details production

# 2. Diagnose issues (shows why containers aren't starting)
dockflow diagnose production

# 3. Check logs
dockflow logs production app -f
dockflow logs production --since 10m

# 4. Shell into a container
dockflow bash production app

# 5. SSH to the server for manual inspection
dockflow ssh production "docker service ls"

# 6. Check deployment history
dockflow audit production
dockflow metrics production --history
```

Enable verbose output during deploy:

```bash
dockflow deploy production --debug
```

## History Replication

Deployment history (audit log and metrics) is automatically replicated to **all cluster nodes** (managers and workers) after each deployment. This ensures:

- No data loss if a manager goes down
- Seamless history access after worker-to-manager promotion
- No fragmented history when manager failover occurs

History is read with automatic fallback: if the primary manager is unreachable, Dockflow tries other managers, then workers.

### Manual Sync

If a node was offline during a deployment or a new node was added to the cluster, manually sync the full history:

```bash
dockflow history-sync production
```

This reads history from all reachable nodes, merges and deduplicates entries, then writes the complete dataset back to every node.

<Callout type="info">
  `history-sync` deduplicates by metric ID (JSONL) and exact line match (audit log), so running it multiple times is safe.
</Callout>
