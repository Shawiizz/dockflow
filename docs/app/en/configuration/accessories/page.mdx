# Accessories

import { Callout, Tabs } from 'nextra/components'

Accessories are **stateful services** (databases, caches, message queues, etc.) that have a separate lifecycle from your main application. They are deployed once and remain untouched during regular app deployments.

## Why Accessories?

<Callout type="warning">
  **Problem**: If you put your database in the main `docker-compose.yml`, it gets restarted on every deployment. This can cause data corruption or downtime.
</Callout>

**Solution**: Accessories have their own lifecycle, deployed once and left alone by app redeploys. On Swarm they are a separate stack; on k3s they live in the same namespace as the app, told apart by a `role` label. Your app can be deployed 100 times without touching the database.

<Tabs items={['Swarm', 'k3s']}>
  <Tabs.Tab>
```
myapp-production              ← Main app (redeployed often)
myapp-production-accessories  ← Databases, Redis, etc. (deployed once)
```
  </Tabs.Tab>
  <Tabs.Tab>
```
dockflow-myapp-production     ← One namespace, two roles
  app services   → role=app
  postgres, redis → role=accessory
```
  </Tabs.Tab>
</Tabs>

## Configuration

Create a file at `.dockflow/docker/accessories.yml` using standard Docker Compose format:

```yaml filename=".dockflow/docker/accessories.yml"
services:
  postgres:
    image: postgres:16-alpine
    ports:
      - "5432:5432"
    volumes:
      - postgres_data:/var/lib/postgresql/data
    environment:
      POSTGRES_USER: app
      POSTGRES_PASSWORD: "{{ db_password }}"
      POSTGRES_DB: myapp
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U app"]
      interval: 10s
      timeout: 5s
      retries: 5

  redis:
    image: redis:8-alpine
    ports:
      - "6379:6379"
    volumes:
      - redis_data:/data
    command: redis-server --appendonly yes
    healthcheck:
      test: ["CMD", "redis-cli", "ping"]
      interval: 10s
      timeout: 5s
      retries: 5

volumes:
  postgres_data:
  redis_data:
```

<Callout type="info">
  Environment variables can be accessed using template syntax: `{{ variable_name }}`
</Callout>

<Callout type="warning">
  Accessory images are always **pulled**, never built. Build targets are collected from
  `docker-compose.yml` only, so a `build:` section in `accessories.yml` is ignored and the
  image named by `image:` is used as-is. To ship a file into an accessory, use
  [File Uploads](/en/configuration/upload) and bind-mount it — uploads complete before any
  accessory starts, so the file is in place when the container comes up.
</Callout>

## Automatic Deploy Configuration

Dockflow automatically injects a minimal deploy configuration for each accessory service:

```yaml
deploy:
  replicas: 1
  restart_policy:
    condition: on-failure
    delay: 5s
    max_attempts: 3
```

This ensures:
- **Single replica** by default (appropriate for stateful services)
- **Automatic restart** on failure with backoff
- **No rolling updates** (you control when to update databases)

You can override any of these in your `accessories.yml`.

## Deployment

Dockflow uses **hash-based change detection** for accessories. This means:

- First deployment → accessories are automatically deployed
- `accessories.yml` changed → accessories are automatically redeployed
- No changes → accessories are skipped (fast)

### Automatic Deployment (Default)

```bash
dockflow deploy production
# Deploys app
# Auto-checks accessories.yml hash
# Deploys accessories only if changed or first time
```

### Force Redeploy Accessories

```bash
dockflow deploy production --accessories  # Accessories only (forced)
dockflow deploy production --all          # App + accessories (forced)
```

### Skip Accessories Check

```bash
dockflow deploy production --skip-accessories
# Deploys app only, completely ignores accessories
```

<Callout type="info">
  The hash is stored on the server at `/var/lib/dockflow/accessories/{stack}/.hash`. Delete this file to force a redeploy on next deployment.
</Callout>

## Management Commands

All accessories commands use SSH to interact with the running services.

### List Accessories

```bash
dockflow accessories list production
# or
dockflow acc ls production
```

Shows all accessories services with their status and replicas.

### View Logs

```bash
dockflow accessories logs production           # All accessories
dockflow accessories logs production postgres  # Specific service
dockflow accessories logs production postgres -f  # Follow
```

### Execute Commands

```bash
dockflow accessories exec production postgres       # Open shell
dockflow accessories exec production postgres psql  # Run psql
```

### Restart Services

```bash
dockflow accessories restart production           # All
dockflow accessories restart production postgres  # Specific
```

### Stop Services

```bash
dockflow accessories stop production           # Scale all to 0
dockflow accessories stop production postgres  # Scale specific to 0
```

<Callout type="info">
  Stop scales services to 0 replicas but keeps the containers (or pods) and volumes. Use `restart` to bring them back.
</Callout>

<Callout type="warning">
  On k3s, an accessory scaled to 0 with `stop` **stays at 0** across ordinary app deploys — change
  detection skips a redeploy of `accessories.yml` when it hasn't changed, so nothing re-applies the
  replica count (Swarm parity). Bring it back with `accessories restart` or a forced
  `deploy --accessories`.
</Callout>

### Remove Accessories

```bash
dockflow accessories remove production           # Remove stack (keep volumes)
dockflow accessories remove production --volumes # Remove stack AND volumes
dockflow accessories remove production --volumes -y  # Skip prompt and typed confirmation (CI)
```

<Callout type="error">
  The `--volumes` flag permanently deletes all data. You will be prompted to type the environment name to confirm, unless `-y`/`--yes` is passed — the only way to skip that typed confirmation, meant for non-interactive CI runs.
</Callout>

<Callout type="info">
  On k3s, PersistentVolumeClaims are never deleted implicitly. Without `--volumes` the claims survive
  the removal and are re-attached the next time the accessory is deployed.
</Callout>

## Best Practices

### 1. Always Use Named Volumes

```yaml
volumes:
  - postgres_data:/var/lib/postgresql/data  # ✅ Named volume
  - ./data:/var/lib/postgresql/data         # ❌ Bind mount (lost on redeploy)
```

### 2. Pin Image Versions

```yaml
image: postgres:16-alpine  # ✅ Specific version
image: postgres:latest     # ❌ Unpredictable updates
```

### 3. Configure Health Checks

```yaml
healthcheck:
  test: ["CMD-SHELL", "pg_isready -U app"]
  interval: 10s
  timeout: 5s
  retries: 5
  start_period: 30s  # Give time for initial startup
```

### 4. Constrain to Manager Node (Optional)

For single-node deployments, this ensures data stays on the same node:

```yaml
deploy:
  placement:
    constraints:
      - node.role == manager
```

## Connecting Your App

<Tabs items={['Swarm', 'k3s']}>
  <Tabs.Tab>
Your main application connects to accessories over the accessories stack's overlay network, using Docker's internal DNS:

```yaml
# .dockflow/docker/docker-compose.yml
services:
  app:
    image: myapp:latest
    environment:
      DATABASE_URL: postgres://app:password@postgres:5432/myapp
      REDIS_URL: redis://redis:6379
    networks:
      - default
      - accessories

networks:
  accessories:
    external: true
    name: myapp-production-accessories_default
```

<Callout type="warning">
  Make sure to reference the correct network name: `{project}-{env}-accessories_default`
</Callout>
  </Tabs.Tab>
  <Tabs.Tab>
App services and accessories share one namespace, so no external network is needed — the plain
compose service name resolves through the namespace's own DNS:

```yaml
# .dockflow/docker/docker-compose.yml
services:
  app:
    image: myapp:latest
    environment:
      DATABASE_URL: postgres://app:password@postgres:5432/myapp
      REDIS_URL: redis://redis:6379
```

No `networks:` section, no external network declaration — `postgres` and `redis` resolve as soon
as the accessories are deployed once, exactly as the Swarm example resolves after joining the
`accessories` network.
  </Tabs.Tab>
</Tabs>

<Callout type="info">
  **Protect your data**: Dockflow supports automated backup and restore for accessories. See [Backup & Restore](/en/configuration/backup) for details.
</Callout>

## Kubernetes (k3s)

<Callout type="info">
  On k3s, accessories are not a second stack: they are the compose services of `accessories.yml`,
  applied into the **same namespace** as the app (`dockflow-{project}-{env}`) and told apart by a
  `role` label (`app` or `accessory`). Prune, apply and stop are scoped by that label, so an app
  deploy never touches accessory objects and vice versa.
</Callout>

- **Naming and DNS.** Because both roles share one namespace, a compose service name resolves
  through plain in-cluster DNS — no `{project}-{env}-accessories_default`-style network to declare.
- **Name collisions are refused.** An app service and an accessory cannot resolve to the same
  Kubernetes name (`services and accessories share the namespace ..., so names must be unique`).
  Rename one of them.
- **Change detection is unchanged.** The same hash-based skip applies: `accessories.yml` unchanged
  means no redeploy, whatever the previous replica count was — see the stop warning above.
- **Volumes.** Accessory PersistentVolumeClaims follow the same rule as the app's: never deleted
  implicitly, kept on `stop` and on a plain `remove`, deleted one at a time only by
  `accessories remove --volumes` (or later by `dockflow volumes rm`).
- **Helm accessory releases.** A `helm.releases[]` entry with `role: accessory` (see
  [Helm Charts](/en/configuration/helm)) follows the accessory lifecycle too: it takes part in the
  same change detection and is never uninstalled implicitly when removed from `config.yml` — Dockflow
  only warns, and `dockflow helm uninstall <env> <name>` removes it by hand.
