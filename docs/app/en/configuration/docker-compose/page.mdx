# Docker Compose

import { Callout } from 'nextra/components'

Dockflow uses a standard `docker-compose.yml` file located at `.dockflow/docker/docker-compose.yml`. This file defines your application services, networks, and volumes.

<Callout type="info">
  On Swarm the file is handed to `docker stack deploy` mostly as written. On k3s it is **translated**
  into Kubernetes objects — most compose keys map directly, some become something else, and a few are
  rejected. See the [compose support table](/en/configuration/kubernetes/compose-support) for the
  exact outcome of every key, and the [Kubernetes overview](/en/configuration/kubernetes) for how
  services, naming, secrets and exposure map.
</Callout>

## Basic Structure

```yaml
services:
  app:
    image: my-app
    build:
      context: ../..
      dockerfile: Dockerfile
    ports:
      - "{{ current.env.app_port }}:3000"
    environment:
      DB_PASSWORD: {{ current.env.db_password }}
      ENV: {{ env }}
    networks:
      - app-network

networks:
  app-network:
```

The `build` section tells Dockflow how to build the image. The `context` is relative to the compose file location (`.dockflow/docker/`), so `../..` points to the project root.

## Environment Variables

Environment variables can come from multiple sources:

- **`servers.yml`** — defined per-environment or per-server (see [Servers & Connections](/en/configuration/servers))
- **CI secrets** — override `servers.yml` values
- **Nunjucks templating** — all files in `.dockflow/` are automatically rendered with Nunjucks. This is the only substitution Dockflow performs.

```yaml
services:
  app:
    image: my-app
    environment:
      ENV: {{ env }}                              # Always in the context
      VERSION: {{ version }}                      # Always in the context
      DB_HOST: {{ current.env.db_host }}          # From servers.yml or CI secrets
      SECRET_KEY: {{ current.env.secret_key }}    # From servers.yml or CI secrets
    ports:
      - "{{ current.env.app_port | default('3000') }}:3000"         # With default value
```

<Callout type="info">
  `{{ env }}` and `{{ version }}` are always available in the render context — no need to declare them in `servers.yml`.
</Callout>

### `$` placeholders vs Nunjucks

Compose itself understands `$VAR` and `${VAR}` shell-style placeholders, with `$$` as the escape for
a literal `$`. Dockflow does not export a process environment for that substitution, so a stray
`$VAR` never resolves to anything useful:

- **On Swarm**, `dockflow validate` and `deploy` warn about every such placeholder it finds
  (`line 12: $DB_HOST — Docker replaces it when deploying, and Dockflow gives it no value`) and
  suggest the Nunjucks equivalent; Docker itself silently substitutes an empty string at deploy time.
- **On k3s**, Dockflow performs the interpolation itself while rendering, so the same placeholder is
  a hard `ConfigError` naming the exact key instead of a warning — nothing is silently emptied.

```yaml
services:
  app:
    environment:
      DB_HOST: $DB_HOST                 # ❌ Docker/Dockflow placeholder, never resolves
      DB_HOST: {{ current.env.db_host }} # ✅ Nunjucks — resolved at render time
      PRICE: "$$19.99"                   # ✅ literal $ via the $$ escape
```

Use `{{ current.env.<var> }}` (or `{{ env }}` / `{{ version }}`) for anything you actually want
substituted, and `$$` whenever a value must contain a literal `$` (a basic-auth htpasswd hash in a
Traefik label, a price string, and so on).

## Automatic Image Tagging

Dockflow automatically appends the environment and version to image names for isolation:

```
my-app → my-app-production:1.0.0
my-app → my-app-staging:abc123
```

When a Docker registry is configured, the registry URL is also prepended:

```
my-app → ghcr.io/myorg/my-app-production:1.0.0
```

This behavior can be disabled with `image_auto_tag: false` in [config.yml](/en/configuration/config-file).

<Callout type="info">
  Auto-tagging only ever retags a service that has a `build:` section — a service that only
  declares `image:` (a pulled, third-party image) is never renamed, on either orchestrator.
</Callout>

## YAML Parsing Notes

- **Anchors and merge keys are resolved.** `<<: *common` is expanded into the file Dockflow sends,
  not re-emitted as a merge key — write one anchor and reuse it across services, the deployed result
  is the merged document.
- **File modes are read as octal.** `mode: 0440` (on `secrets`/`configs` entries, or an
  `x-dockflow` file mount) is parsed the way `chmod` reads it — as octal, not decimal. Writing the
  value without the leading `0` (`mode: 440`) is read as the *decimal* number 440 and a warning
  names the octal value you probably meant.
- **Scalars keep their written text.** `PORT: 010` in `environment` or a label stays the string
  `"010"` — Compose's own YAML rules apply, not a numeric reinterpretation.

## Deploy Configuration

The `deploy` section controls how the orchestrator manages your services. Dockflow injects sensible defaults for Swarm — on k3s these settings are translated to Kubernetes resource equivalents. You only need to specify what you want to override.

### Default Values

Dockflow automatically injects these deploy settings for application services:

| Setting | Default |
|---------|---------|
| `update_config.parallelism` | 1 |
| `update_config.delay` | 10s |
| `update_config.failure_action` | rollback |
| `update_config.monitor` | 30s |
| `update_config.order` | start-first |
| `update_config.max_failure_ratio` | 0 |
| `rollback_config.parallelism` | 1 |
| `rollback_config.delay` | 5s |
| `rollback_config.monitor` | 15s |
| `rollback_config.order` | start-first |

Your compose file values always take priority over these defaults.

### Replicas and Resources

```yaml
services:
  app:
    image: my-app
    deploy:
      replicas: 3
      resources:
        limits:
          cpus: "1.0"
          memory: 512M
        reservations:
          cpus: "0.25"
          memory: 128M
```

### Custom Update Strategy

```yaml
services:
  app:
    image: my-app
    deploy:
      replicas: 2
      update_config:
        parallelism: 1
        delay: 30s
        order: start-first        # Start new before stopping old (zero-downtime)
        failure_action: rollback
      rollback_config:
        parallelism: 1
        order: start-first
```

## Health Checks

Docker health checks let the orchestrator verify that containers are actually working:

```yaml
services:
  app:
    image: my-app
    healthcheck:
      test: ["CMD", "curl", "-f", "http://localhost:3000/health"]
      interval: 30s
      timeout: 10s
      retries: 3
      start_period: 40s
```

<Callout type="info">
  Dockflow also supports its own [health check system](/en/configuration/config-file#health-checks) that runs external HTTP checks after deployment, independently of Docker's built-in health checks.
</Callout>

## Volumes

```yaml
services:
  app:
    image: my-app
    volumes:
      - app-data:/app/data
      - /host/path:/container/path    # Bind mount

volumes:
  app-data:
```

<Callout type="info">
  On Swarm, volumes and networks are automatically prefixed with the stack name (e.g., `myapp-production_app-data`). On k3s, resources are scoped to the `dockflow-{stackName}` namespace.
</Callout>

## Networks

```yaml
services:
  app:
    image: my-app
    networks:
      - frontend
      - backend

  db:
    image: postgres:16
    networks:
      - backend

networks:
  frontend:
  backend:
```

### External networks (Swarm only)

When a network is marked `external: true`, Dockflow automatically creates it on the Swarm manager before deploying if it doesn't already exist:

```yaml
services:
  app:
    networks:
      - shared-net

networks:
  shared-net:
    external: true
```

This is useful when multiple independent stacks need to communicate over a shared overlay network. Dockflow creates the network with `--driver overlay --attachable` so any stack can attach to it.

<Callout type="info">
  For communication between an app stack and its accessories stack within the same project, you don't need an external network. Use the Swarm DNS name directly: `{{ project_name }}-{{ env }}-accessories_servicename`.
</Callout>

## Placement Constraints

For multi-host deployments, you can control which nodes run each service:

```yaml
services:
  app:
    image: my-app
    deploy:
      placement:
        constraints:
          - node.role == manager
          - node.hostname == server-1

  worker:
    image: my-worker
    deploy:
      placement:
        constraints:
          - node.role == worker
```

See [Multi-Host Deployment](/en/configuration/multi-host) for details on configuring a multi-node cluster.

## Multi-Service Example

```yaml
services:
  frontend:
    image: my-frontend
    build:
      context: ../..
      dockerfile: Dockerfile.frontend
    ports:
      - "80:80"
      - "443:443"
    environment:
      API_URL: http://backend:3000
    networks:
      - frontend
    deploy:
      replicas: 2

  backend:
    image: my-backend
    build:
      context: ../..
      dockerfile: Dockerfile.backend
    environment:
      DB_HOST: {{ current.env.db_host }}
      DB_PASSWORD: {{ current.env.db_password }}
      REDIS_URL: redis://redis:6379
    networks:
      - frontend
      - backend
    deploy:
      replicas: 3
    healthcheck:
      test: ["CMD", "curl", "-f", "http://localhost:3000/health"]
      interval: 30s
      timeout: 5s
      retries: 3

networks:
  frontend:
  backend:
```

## Environment Isolation

Dockflow ensures complete isolation between environments (production, staging, etc.) through:

1. **Image names** — automatically tagged with environment and version (`my-app-production:1.0.0`)
2. **Stack names** — each environment gets its own isolated stack or namespace
3. **Networks and volumes** — scoped per stack (Swarm prefix, k3s namespace)
