# Docker Compose

import { Callout } from 'nextra/components'

Dockflow uses a standard `docker-compose.yml` file located at `.dockflow/docker/docker-compose.yml`. This file defines your application services, networks, and volumes.

## Basic Structure

```yaml
services:
  app:
    image: my-app
    build:
      context: ../..
      dockerfile: Dockerfile
    ports:
      - "{{ current.env.app_port }}:3000"
    environment:
      DB_PASSWORD: {{ current.env.db_password }}
      ENV: {{ env }}
    networks:
      - app-network

networks:
  app-network:
```

The `build` section tells Dockflow how to build the image. The `context` is relative to the compose file location (`.dockflow/docker/`), so `../..` points to the project root.

## Environment Variables

Environment variables can come from multiple sources:

- **`servers.yml`** — defined per-environment or per-server (see [Servers & Connections](/en/configuration/servers))
- **CI secrets** — override `servers.yml` values
- **Nunjucks templating** — all files in `.dockflow/` are automatically rendered with Nunjucks. This is the only substitution Dockflow performs. Shell-style `$VAR` and `${VAR}` placeholders are left to Docker, which replaces them with an empty string as no env file is given: `dockflow validate` reports each one as an error with its line, and `deploy` warns. Write `$$` for a literal `$`.

```yaml
services:
  app:
    image: my-app
    environment:
      ENV: {{ env }}                              # Always in the context
      VERSION: {{ version }}                      # Always in the context
      DB_HOST: {{ current.env.db_host }}          # From servers.yml or CI secrets
      SECRET_KEY: {{ current.env.secret_key }}    # From servers.yml or CI secrets
    ports:
      - "{{ current.env.app_port | default('3000') }}:3000"         # With default value
```

<Callout type="info">
  `{{ env }}` and `{{ version }}` are always available in the render context — no need to declare them in `servers.yml`.
</Callout>

## How the File Is Read

Dockflow reads the compose file the way Compose means it, then hands Swarm a plain file:

- Merge keys (`<<: *defaults`) are resolved, and an anchor used twice gives two independent copies.
- File modes such as `mode: 0440` on secrets, configs and tmpfs are octal, as Compose reads them.
- Values Compose treats as text keep their text: `PORT: 010` stays `010`, `VERSION: 1.10` stays `1.10` (environment, labels, build args, sysctls, extra hosts).
- A file that Compose would not mean is refused with its name and line: duplicate keys, several YAML documents, tags other than the plain YAML ones (`!reset` and `!override` belong to override files, which Dockflow does not merge).
- A file holding only comments is a stack without services.

## Automatic Image Tagging

Dockflow automatically appends the environment and version to the names of the images it builds (services with a `build:` section), for isolation. An image it does not build, such as `postgres:16`, is pulled as written.

```
my-app → my-app-production:1.0.0
my-app → my-app-staging:abc123
```

When a Docker registry is configured, the registry URL is also prepended:

```
my-app → ghcr.io/myorg/my-app-production:1.0.0
```

This behavior can be disabled with `image_auto_tag: false` in [config.yml](/en/configuration/config-file).

## Deploy Configuration

The `deploy` section controls how Swarm manages your services. Dockflow injects sensible defaults; you only need to specify what you want to override.

### Default Values

Dockflow automatically injects these deploy settings for application services:

| Setting | Default |
|---------|---------|
| `update_config.parallelism` | 1 |
| `update_config.delay` | 10s |
| `update_config.failure_action` | rollback |
| `update_config.monitor` | 30s |
| `update_config.order` | start-first |
| `update_config.max_failure_ratio` | 0 |
| `rollback_config.parallelism` | 1 |
| `rollback_config.delay` | 5s |
| `rollback_config.monitor` | 15s |
| `rollback_config.order` | start-first |

Your compose file values always take priority over these defaults.

### Replicas and Resources

```yaml
services:
  app:
    image: my-app
    deploy:
      replicas: 3
      resources:
        limits:
          cpus: "1.0"
          memory: 512M
        reservations:
          cpus: "0.25"
          memory: 128M
```

### Custom Update Strategy

```yaml
services:
  app:
    image: my-app
    deploy:
      replicas: 2
      update_config:
        parallelism: 1
        delay: 30s
        order: start-first        # Start new before stopping old (zero-downtime)
        failure_action: rollback
      rollback_config:
        parallelism: 1
        order: start-first
```

## Health Checks

Docker health checks let Swarm verify that containers are actually working:

```yaml
services:
  app:
    image: my-app
    healthcheck:
      test: ["CMD", "curl", "-f", "http://localhost:3000/health"]
      interval: 30s
      timeout: 10s
      retries: 3
      start_period: 40s
```

<Callout type="info">
  Dockflow also supports its own [health check system](/en/configuration/config-file#health-checks) that runs external HTTP checks after deployment, independently of Docker's built-in health checks.
</Callout>

## Volumes

```yaml
services:
  app:
    image: my-app
    volumes:
      - app-data:/app/data
      - /host/path:/container/path    # Bind mount

volumes:
  app-data:
```

<Callout type="info">
  Volumes and networks are automatically prefixed with the stack name (e.g., `myapp-production_app-data`).
</Callout>

## Networks

```yaml
services:
  app:
    image: my-app
    networks:
      - frontend
      - backend

  db:
    image: postgres:16
    networks:
      - backend

networks:
  frontend:
  backend:
```

### External networks (Swarm only)

When a network is marked `external: true`, Dockflow automatically creates it on the Swarm manager before deploying if it doesn't already exist:

```yaml
services:
  app:
    networks:
      - shared-net

networks:
  shared-net:
    external: true
```

This is useful when multiple independent stacks need to communicate over a shared overlay network. Dockflow creates the network with `--driver overlay --attachable` so any stack can attach to it.

<Callout type="info">
  For communication between an app stack and its accessories stack within the same project, you don't need an external network. Use the Swarm DNS name directly: `{{ project_name }}-{{ env }}-accessories_servicename`.
</Callout>

## Placement Constraints

For multi-host deployments, you can control which nodes run each service:

```yaml
services:
  app:
    image: my-app
    deploy:
      placement:
        constraints:
          - node.role == manager
          - node.hostname == server-1

  worker:
    image: my-worker
    deploy:
      placement:
        constraints:
          - node.role == worker
```

See [Multi-Host Deployment](/en/configuration/multi-host) for details on configuring a multi-node cluster.

## Multi-Service Example

```yaml
services:
  frontend:
    image: my-frontend
    build:
      context: ../..
      dockerfile: Dockerfile.frontend
    ports:
      - "80:80"
      - "443:443"
    environment:
      API_URL: http://backend:3000
    networks:
      - frontend
    deploy:
      replicas: 2

  backend:
    image: my-backend
    build:
      context: ../..
      dockerfile: Dockerfile.backend
    environment:
      DB_HOST: {{ current.env.db_host }}
      DB_PASSWORD: {{ current.env.db_password }}
      REDIS_URL: redis://redis:6379
    networks:
      - frontend
      - backend
    deploy:
      replicas: 3
    healthcheck:
      test: ["CMD", "curl", "-f", "http://localhost:3000/health"]
      interval: 30s
      timeout: 5s
      retries: 3

networks:
  frontend:
  backend:
```

## Environment Isolation

Dockflow ensures complete isolation between environments (production, staging, etc.) through:

1. **Image names** — automatically tagged with environment and version (`my-app-production:1.0.0`)
2. **Stack names** — each environment gets its own isolated stack
3. **Networks and volumes** — scoped per stack (prefixed with the stack name)
