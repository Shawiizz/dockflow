# Multi-Node Deployment

import { Callout, Tabs } from 'nextra/components'

Deploy your application across multiple servers. Multi-node clusters are supported on both
**Docker Swarm** and **k3s**.

<Callout type="info">
  The orchestrator is selected with `orchestrator: swarm | k3s` in `config.yml`. See [Orchestrator](/en/configuration/orchestrator) for details.
</Callout>

## Architecture

<Tabs items={['Swarm', 'k3s']}>
  <Tabs.Tab>
    - **Managers**: Receive deployments and orchestrate the cluster
    - **Workers**: Run containers distributed by managers
    - **Multi-manager**: For high availability (tolerates manager failures)
  </Tabs.Tab>
  <Tabs.Tab>
    A `manager` in `servers.yml` becomes a k3s **server** (control plane + embedded etcd when there
    is more than one); a `worker` becomes a k3s **agent**, which only runs workloads. Deploys, Helm
    releases and day-2 commands run over SSH on a control-plane node, exactly like Swarm targets a
    manager.

    <Callout type="warning">
      An HA k3s cluster needs an **odd number** of managers — **1, 3 or 5** (an embedded-etcd cluster
      of `2n` members tolerates no more failures than one of `2n - 1`, so an even count buys nothing).
      An even count is refused before any SSH connection:

      ```
      servers: tag "production" has 4 managers; an embedded-etcd cluster needs an odd number, so declare 1 or 3
      ```
    </Callout>
  </Tabs.Tab>
</Tabs>

## Basic Configuration

```yaml
# .dockflow/servers.yml

servers:
  manager:
    role: manager
    tags: [production]

  worker1:
    role: worker
    tags: [production]

  worker2:
    role: worker
    tags: [production]

defaults:
  user: dockflow
  port: 22
```

Each server needs a connection string in your secrets:

```bash
PRODUCTION_MANAGER_CONNECTION=eyJob3N0Ijoi...
PRODUCTION_WORKER1_CONNECTION=eyJob3N0Ijoi...
PRODUCTION_WORKER2_CONNECTION=eyJob3N0Ijoi...
```

<Tabs items={['Swarm', 'k3s']}>
  <Tabs.Tab>
    <Callout type="info">
      Workers automatically join the Swarm cluster during `dockflow setup swarm`. You only deploy to the manager — Swarm distributes workloads automatically.
    </Callout>
  </Tabs.Tab>
  <Tabs.Tab>
    <Callout type="info">
      Agents automatically join the cluster during `dockflow setup k3s`. You only deploy to a
      control-plane node — k3s's scheduler and Dockflow's [node labels](#private-ip-and-node-labels)
      place workloads across servers and agents.
    </Callout>
  </Tabs.Tab>
</Tabs>

## Multi-Manager for High Availability

For production environments, configure multiple managers for failover:

<Tabs items={['Swarm', 'k3s']}>
  <Tabs.Tab>
```yaml
# .dockflow/servers.yml
servers:
  manager1:
    role: manager
    tags: [production]

  manager2:
    role: manager
    tags: [production]

  manager3:
    role: manager
    tags: [production]

  worker1:
    role: worker
    tags: [production]

  worker2:
    role: worker
    tags: [production]
```

<Callout type="warning">
  For Raft consensus, use an **odd number** of managers:
  - 3 managers = tolerates 1 failure
  - 5 managers = tolerates 2 failures
</Callout>
  </Tabs.Tab>
  <Tabs.Tab>
```yaml
# .dockflow/servers.yml
servers:
  manager1:
    role: manager
    private_host: 10.0.0.11
    tags: [production]

  manager2:
    role: manager
    private_host: 10.0.0.12
    tags: [production]

  manager3:
    role: manager
    private_host: 10.0.0.13
    tags: [production]

  worker1:
    role: worker
    private_host: 10.0.0.21
    tags: [production]
```

The first manager `dockflow setup k3s` reaches becomes the embedded-etcd cluster's initializer
(`--cluster-init`); the rest join it. Use an odd manager count — see the callout above.
  </Tabs.Tab>
</Tabs>

## Automatic Failover

<Tabs items={['Swarm', 'k3s']}>
  <Tabs.Tab>
When deploying with multiple managers, Dockflow automatically:

1. Checks each manager's status via SSH
2. Finds the active Swarm leader (or any reachable manager)
3. Falls back to the next available manager if one is down

```bash
# Dockflow finds the active leader automatically
dockflow deploy production

# Disable failover (use first manager only)
dockflow deploy production --no-failover
```

Example output with failover:
```
⠋ Checking 3 managers for active leader...
  Checking manager1... ✗ unreachable
  Checking manager2... ✓ LEADER
⚠ Using manager2 (leader). Unreachable: manager1 (unreachable)
```
  </Tabs.Tab>
  <Tabs.Tab>
There is no leader election to probe: any control-plane node that answers the Kubernetes API can run
a deploy. Dockflow tries each manager in `servers.yml` order and targets the first one whose API
answers `get --raw=/readyz`:

```bash
dockflow deploy production
dockflow deploy production --no-failover  # first manager only
dockflow deploy production --server manager2  # target one explicitly
```

```
⠋ Checking 3 managers...
  Checking manager1... ✗ unreachable
  Checking manager2... ✓ Ready
⚠ Using manager2. Unreachable: manager1 (unreachable)
```

<Callout type="error">
  **What survives a failover, and what does not.** Releases, the deploy lock and
  `dockflow status`/`version` live *in the cluster* (Secrets and a Lease), so they are identical from
  every manager. `dockflow history`, `audit` and `metrics`, on the other hand, read the log files of
  one manager — the first one that answers, printed by the command — and backups are stored on the
  manager that took them. After a failover, those three show only the reachable manager's view until
  the lost node comes back.
</Callout>
  </Tabs.Tab>
</Tabs>

## How Deployment Works

<Tabs items={['Swarm', 'k3s']}>
  <Tabs.Tab>
1. **Deploy targets the manager** — Dockflow connects only to the active manager
2. **Swarm schedules workloads** — Containers are distributed across all nodes automatically
3. **Images are transferred to workers** — Via SSH streaming or [registry](/en/configuration/registry)

```bash
dockflow deploy production
# ✓ Deployment completed! Swarm cluster: 3 managers, 2 worker(s)
```
  </Tabs.Tab>
  <Tabs.Tab>
1. **Deploy targets one control-plane node** — Dockflow connects over SSH and runs `kubectl`/`helm` there
2. **Kubernetes schedules workloads** — the scheduler places pods across every server and agent, honouring `node_labels` and `x-dockflow.node_selector`
3. **Images are imported on every eligible node** — via SSH streaming into containerd, or a [registry](/en/configuration/registry) pull Secret

```bash
dockflow deploy production
# ✓ Deployment completed! k3s cluster: 3 servers, 2 agent(s)
```
  </Tabs.Tab>
</Tabs>

## Private IP and Node Labels

k3s-only `servers.yml` fields for multi-node clusters:

```yaml
# .dockflow/servers.yml
servers:
  manager1:
    role: manager
    host: 203.0.113.10          # public IP, used for SSH
    private_host: 10.0.0.11     # cluster traffic: node IP, firewall sources, etcd/join address
    tags: [production]

  worker1:
    role: worker
    host: 203.0.113.20
    private_host: 10.0.0.21
    tags: [production]
    node_labels:
      zone: a
      disk: ssd
```

| Field | Description |
|---|---|
| `private_host` | Address used for cluster traffic: the k3s node IP, the address firewall rules restrict cluster ports to, and the join address between servers/agents. Defaults to `host`. Only IPv4 is supported so far — an IPv6 `private_host` is refused at setup. |
| `node_labels` | Kubernetes node labels applied by `dockflow setup k3s`, consumed by `x-dockflow.node_selector` (see [Docker Compose](/en/configuration/docker-compose)) to pin services to specific nodes. |

<Callout type="info">
  When every node talks over its public address (`private_host` unset), flannel falls back to a
  wireguard-native backend automatically, so cluster traffic between nodes stays encrypted even
  across the internet.
</Callout>

## Server-Specific Environment Variables

Override variables for specific servers:

```yaml
# .dockflow/servers.yml
servers:
  manager1:
    role: manager
    tags: [production]
    env:
      NODE_ID: "manager-1"
      PROMETHEUS_ENABLED: "true"

  worker1:
    role: worker
    tags: [production]
    env:
      NODE_ID: "worker-1"
      GPU_ENABLED: "true"
```
