# Docker Compose

import { Callout } from 'nextra/components'

Dockflow utilise un fichier `docker-compose.yml` standard situé à `.dockflow/docker/docker-compose.yml`. Ce fichier définit vos services applicatifs, réseaux, et volumes.

## Structure de base

```yaml
services:
  app:
    image: my-app
    build:
      context: ../..
      dockerfile: Dockerfile
    ports:
      - "{{ current.env.app_port }}:3000"
    environment:
      DB_PASSWORD: {{ current.env.db_password }}
      ENV: {{ env }}
    networks:
      - app-network

networks:
  app-network:
```

La section `build` indique à Dockflow comment construire l'image. Le `context` est relatif à l'emplacement du fichier compose (`.dockflow/docker/`), donc `../..` pointe vers la racine du projet.

## Variables d'environnement

Les variables d'environnement peuvent provenir de plusieurs sources :

- **`servers.yml`** — définies par environnement ou par serveur (voir [Serveurs & Connexions](/fr/configuration/servers))
- **Secrets CI** — surchargent les valeurs de `servers.yml`
- **Templating Nunjucks** — tous les fichiers dans `.dockflow/` sont automatiquement rendus avec Nunjucks

```yaml
services:
  app:
    image: my-app
    environment:
      ENV: {{ env }}                              # Toujours dans le contexte
      VERSION: {{ version }}                      # Toujours dans le contexte
      DB_HOST: {{ current.env.db_host }}                # Depuis servers.yml ou les secrets CI
      SECRET_KEY: {{ current.env.secret_key }}          # Depuis servers.yml ou les secrets CI
    ports:
      - "{{ current.env.app_port | default('3000') }}:3000"         # Avec valeur par défaut
```

<Callout type="info">
  `{{ env }}` et `{{ version }}` sont toujours disponibles — Dockflow les injecte automatiquement pendant le déploiement.
</Callout>

## Tagging automatique des images

Dockflow ajoute automatiquement l'environnement et la version aux noms d'images pour l'isolation :

```
my-app → my-app-production:1.0.0
my-app → my-app-staging:abc123
```

Quand un registre Docker est configuré, l'URL du registre est aussi préfixée :

```
my-app → ghcr.io/myorg/my-app-production:1.0.0
```

Ce comportement peut être désactivé avec `image_auto_tag: false` dans [config.yml](/fr/configuration/config-file).

## Configuration de déploiement

La section `deploy` contrôle comment l'orchestrateur gère vos services. Dockflow injecte des valeurs par défaut sensées pour Swarm — sur k3s ces paramètres sont traduits en équivalents de ressources Kubernetes. Vous n'avez besoin de spécifier que ce que vous voulez surcharger.

### Valeurs par défaut

Dockflow injecte automatiquement ces paramètres de déploiement pour les services applicatifs :

| Paramètre | Défaut |
|---------|---------|
| `update_config.parallelism` | 1 |
| `update_config.delay` | 10s |
| `update_config.failure_action` | rollback |
| `update_config.monitor` | 30s |
| `update_config.order` | start-first |
| `update_config.max_failure_ratio` | 0 |
| `rollback_config.parallelism` | 1 |
| `rollback_config.delay` | 5s |
| `rollback_config.monitor` | 15s |
| `rollback_config.order` | start-first |

Les valeurs de votre fichier compose ont toujours priorité sur ces valeurs par défaut.

### Replicas et ressources

```yaml
services:
  app:
    image: my-app
    deploy:
      replicas: 3
      resources:
        limits:
          cpus: "1.0"
          memory: 512M
        reservations:
          cpus: "0.25"
          memory: 128M
```

### Stratégie de mise à jour personnalisée

```yaml
services:
  app:
    image: my-app
    deploy:
      replicas: 2
      update_config:
        parallelism: 1
        delay: 30s
        order: start-first        # Démarre le nouveau avant d'arrêter l'ancien (zero-downtime)
        failure_action: rollback
      rollback_config:
        parallelism: 1
        order: start-first
```

## Health Checks

Les health checks Docker permettent à l'orchestrateur de vérifier que les conteneurs fonctionnent réellement :

```yaml
services:
  app:
    image: my-app
    healthcheck:
      test: ["CMD", "curl", "-f", "http://localhost:3000/health"]
      interval: 30s
      timeout: 10s
      retries: 3
      start_period: 40s
```

<Callout type="info">
  Dockflow supporte aussi son propre [système de health check](/fr/configuration/config-file#health-checks) qui exécute des vérifications HTTP externes après le déploiement, indépendamment des health checks intégrés de Docker.
</Callout>

## Volumes

```yaml
services:
  app:
    image: my-app
    volumes:
      - app-data:/app/data
      - /host/path:/container/path    # Bind mount

volumes:
  app-data:
```

<Callout type="info">
  Sur Swarm, les volumes et réseaux sont automatiquement préfixés avec le nom de la stack (ex. `myapp-production_app-data`). Sur k3s, les ressources sont scopées au namespace `dockflow-{stackName}`.
</Callout>

## Réseaux

```yaml
services:
  app:
    image: my-app
    networks:
      - frontend
      - backend

  db:
    image: postgres:16
    networks:
      - backend

networks:
  frontend:
  backend:
```

### Réseaux externes (Swarm uniquement)

Quand un réseau est marqué `external: true`, Dockflow le crée automatiquement sur le manager Swarm avant le déploiement s'il n'existe pas déjà :

```yaml
services:
  app:
    networks:
      - shared-net

networks:
  shared-net:
    external: true
```

Utile quand plusieurs stacks indépendantes doivent communiquer sur un réseau overlay partagé. Dockflow crée le réseau avec `--driver overlay --attachable` pour que n'importe quelle stack puisse s'y attacher.

<Callout type="info">
  Pour la communication entre une stack app et sa stack d'accessoires au sein du même projet, vous n'avez pas besoin d'un réseau externe. Utilisez directement le nom DNS Swarm : `{{ project_name }}-{{ env }}-accessories_servicename`.
</Callout>

## Contraintes de placement

Pour les déploiements multi-hôtes, vous pouvez contrôler quels nœuds font tourner chaque service :

```yaml
services:
  app:
    image: my-app
    deploy:
      placement:
        constraints:
          - node.role == manager
          - node.hostname == server-1

  worker:
    image: my-worker
    deploy:
      placement:
        constraints:
          - node.role == worker
```

Voir [Déploiement multi-hôtes](/fr/configuration/multi-host) pour les détails sur la configuration d'un cluster multi-nœuds.

## Exemple multi-services

```yaml
services:
  frontend:
    image: my-frontend
    build:
      context: ../..
      dockerfile: Dockerfile.frontend
    ports:
      - "80:80"
      - "443:443"
    environment:
      API_URL: http://backend:3000
    networks:
      - frontend
    deploy:
      replicas: 2

  backend:
    image: my-backend
    build:
      context: ../..
      dockerfile: Dockerfile.backend
    environment:
      DB_HOST: {{ current.env.db_host }}
      DB_PASSWORD: {{ current.env.db_password }}
      REDIS_URL: redis://redis:6379
    networks:
      - frontend
      - backend
    deploy:
      replicas: 3
    healthcheck:
      test: ["CMD", "curl", "-f", "http://localhost:3000/health"]
      interval: 30s
      timeout: 5s
      retries: 3

networks:
  frontend:
  backend:
```

## Isolation des environnements

Dockflow garantit une isolation complète entre les environnements (production, staging, etc.) via :

1. **Noms d'images** — automatiquement tagués avec l'environnement et la version (`my-app-production:1.0.0`)
2. **Noms de stack** — chaque environnement a sa propre stack ou namespace isolé
3. **Réseaux et volumes** — scopés par stack (préfixe Swarm, namespace k3s)
