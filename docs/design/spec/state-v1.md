# Cluster state, version 1

All of Dockflow's state on a cluster lives in Swarm objects ([ADR-0007](../adr/0007-state-in-raft.md)). This document fixes their names, labels and contents. Its version, `schema: 1`, changes only in a major release of Dockflow.

## Conventions

- **Labels:** every object Dockflow creates carries `dockflow.kind` and `dockflow.schema=1`. Objects of an app environment also carry:
  - `dockflow.app`, `dockflow.env`;
  - `com.docker.stack.namespace=<stack>`, so `docker stack ps` and `docker stack services` work on Dockflow stacks.
- **Names:** Swarm limits config and secret names to 64 characters and service names to 63. With the [name rules](config-v1.md#names) (stack at most 37 characters), every name below fits.
- **Compare-and-swap:** a mutable label is changed only with a compare-and-swap. The update names the version index the agent last read, and a conflict means someone else wrote first. Config data is immutable; only labels change.
- **Clocks:** no algorithm depends on clocks agreeing between machines. Timestamps in labels are informational, written in UTC by the writer.

## Objects

| Kind | Name | Type | Data | Mutable labels |
|---|---|---|---|---|
| `cluster` | `dockflow-cluster` | config | JSON, creation info | `dockflow.system-version`, `dockflow.registry-port`, `dockflow.acme-email`, `dockflow.private-cidrs`, `dockflow.overlay-encryption` |
| `env` | `dockflow-env-<stack>` | config | JSON `{app, env, created_at}` | `dockflow.last-seq`, `dockflow.current`, `dockflow.previous`, `dockflow.degraded` |
| `lock` | `dockflow-lock-<stack>`, or `dockflow-lock-cluster` | config | JSON `{scope, created_at}` | see [Lock](#lock) |
| `release` | `dockflow-release-<stack>-<seq>` (`seq` as 6 digits) | config | gzip of the [release record](#release-record) | `dockflow.status`, `dockflow.finished-at`, `dockflow.rollback-of` |
| `routes` | `dockflow-routes-<stack>-<hash8>` | config | JSON list of routes | `dockflow.active` |
| app secret | `<stack>_secret_<hash12>` | secret | the value | none |
| app config | `<stack>_config_<hash12>` | config | the content | none |
| run | `dockflow-run-<run-id>` | container | – | none |

Where a name has a hash, it is the first 12 hex digits (8 for routes, to fit the 64-character limit) of the SHA-256 of the object's content. A changed value therefore means a new object, never an update.

`<run-id>` is a lowercase ULID, generated by the CLI.

## Lock

There is one lock per environment, `dockflow-lock-<stack>`, and one for the cluster, `dockflow-lock-cluster`. Operations take it as follows:

| Lock | Taken by |
|---|---|
| Environment lock | `deploy`, `rollback`, `backup run`, `backup restore` |
| Cluster lock | `cluster upgrade`, `cluster proxy sync`, `cluster label` |
| Neither | Read-only commands, and `run` |

`dockflow run` takes no lock, because an interactive console would block deploys for its whole duration. Its job service carries the label `dockflow.oneoff=true`, which the planner ignores, so a concurrent deploy neither removes nor updates it.

A lock config is created once and **never deleted**. Its labels:

| Label | Meaning |
|---|---|
| `dockflow.state` | `held` or `free` |
| `dockflow.holder` | The run id of the holder |
| `dockflow.op` | The holder's operation (`deploy`, `rollback`, …) |
| `dockflow.by` | `user@machine` of whoever started the run, and the CI provider when there is one |
| `dockflow.since` | When it was taken (informational) |
| `dockflow.beat` | A counter the holder increments |

The heartbeat interval is 15 s and the lease is 60 s. Both are constants of v1.

**Acquire:**

1. Create the config with `state=held`. If that succeeds, the lock is taken.
2. If it already exists, inspect it.
   - If `state=free`, compare-and-swap it to `held` with the new holder. A conflict means someone else wrote first: start again at step 2.
   - If `state=held`, watch `dockflow.beat` using the local monotonic clock:
     - if it changes, the holder is alive, and the attempt fails with `LockHeld` (holder, operation, since, by). With `--wait`, it keeps waiting instead;
     - if the object's version stays unchanged for a full lease, the holder is dead. Compare-and-swap it to the new holder (a takeover, reported as `lock.taken_over`).

**Renew:** every 15 s, compare-and-swap `beat+1`. A conflict means the lock was taken over: the run emits `lock.lost`, makes no further change and exits with the lock-lost code. The new holder plans from the actual state ([ADR-0008](../adr/0008-plan-apply-releases.md)).

**Release:** compare-and-swap to `state=free` and clear the holder.

A holder that cannot reach a Raft quorum cannot renew, but it cannot change anything else either: both writes need the quorum.

## Release lifecycle

```
applying ──► active ──► superseded
   │
   ├──► rolled-back     the run failed and the previous release was restored
   ├──► failed          the run failed and so did its rollback (environment degraded)
   └──► abandoned       the agent died; found by the next holder of the lock
```

**Sequence numbers:** under the environment lock, the agent compare-and-swaps `dockflow.last-seq` on the environment record to `n+1` and creates `dockflow-release-<stack>-<n+1>` with `status=applying`.

**On success**, the agent updates, in this order:

1. the new release becomes `active`;
2. the previous active release becomes `superseded`;
3. the environment record gets `current=n+1` and `previous=<old current>`, and loses `degraded`.

**Retention:** after a successful run, the agent keeps:

- the newest `releases.keep` releases with status `active` or `superseded`;
- every release newer than the oldest of those.

It deletes the other releases, then the app secrets, app configs, routes objects and registry manifests that no kept release references.

## Release record

The data of a release config is a gzipped JSON document:

```json
{
  "schema": 1,
  "app": "shop",
  "env": "production",
  "seq": 42,
  "version": "a1b2c3d",
  "run": "01jbx6k3m8w0v7c9q2r5t4y6z8",
  "created_at": "2026-10-25T14:03:11Z",
  "created_by": { "user": "shawiizz", "machine": "laptop", "ci": null },
  "source": { "git_sha": "a1b2c3d4e5…", "dirty": false },
  "dockflow_version": "2.0.0",
  "services": {
    "web": { "spec": { "…": "Swarm ServiceSpec as sent to the Engine" }, "image": "127.0.0.1:5959/shop/web@sha256:…" }
  },
  "jobs": {
    "migrate": { "spec": { "…": "…" }, "when": "before", "image": "…" }
  },
  "networks": ["shop-production_default"],
  "volumes": ["shop-production_pgdata"],
  "secrets": ["shop-production_secret_9f2c1ab3e4d5"],
  "configs": [],
  "routes": "dockflow-routes-shop-production-4be1c0aa",
  "published_ports": [],
  "plan_fingerprint": "sha256:…"
}
```

The `spec` of each service is exactly what was sent to the Engine. A rollback sends it again unchanged.

A release record must stay under 1000 KB after compression, the limit of a Swarm config. An app that exceeds it fails at plan time with an explicit error.
